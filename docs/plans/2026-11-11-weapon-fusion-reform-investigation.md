# 武器、道具与升级链改革前调查需求（交给 Claude）

> 日期：2026-11-11。
> 任务性质：调查与证据交付，不是改革实施方案。请先完整调查当前默认分支，再据此提供可供设计决策的数据。
> 不修改正式配方、武器数值、掉落、UI 或存档格式；必要时可添加只读导出工具。不要提前删除铸造升级，也不要自动把全部升级链改成合成链。

## 1. 调查目的与最新设计背景

用户倾向将局内成长转向相邻道具合成，局外铁匠铺保留按已解锁配方打造。需要知道现有内容与系统实际支持什么、迁移会影响什么，再编写改进方案。

### 1.1 用户明确表达的规则与方向

- 红武代表独特身份；同名/同身份红武在一个存档中只能有一件，遗失、销毁或出售后才可能再次获得。不同 Boss 与任务链红武有不同名字，不是整个存档只能有一把红武。
- 局内合成采用特定道具组合，不因投入材料稀有度不同而随机浮动伤害、冷却、耐力消耗。用户认可成品属性体现组合材料特点；当前倾向由配方定义固定成品，不新增随机掷值。
- 正确组合出现“可合成”提示后，只有已解锁成品图鉴才可查看结果；若以前获得过成品，可以看到，否则显示“？？？”。
- 首次成功合成后，在输入武器、组合材料和成品悬浮窗里关联该配方，表达“可与 XX 合成 YY”或“由 XX 和 YY 合成”。
- 只让部分武器参与合成，组合数量适当收敛，不追求所有武器都有完整逐级升级路线。
- 用户提出部分高阶武器既可局外打造也可局内合成，另一些仅可局内合成；允许考虑 Boss 专属金武/红武，现有任务链唯一红武保持各自身份。

### 1.2 仍需调查后决策，不能擅自认定已落地

- 具体保留哪些合成、迁移哪些铸造升级、哪些武器直接获取；最终数量与路线名单。
- 局外打造是否有材料导致的属性差异、现有品质系统如何处理；不能借固定合成结果之名直接删除旧品质机制。
- 在地面、托付、回购列表等仍可取回的红武算不算“已遗失/已出售”，重复掉落如何处理，一次性任务红武如何重新获得。
- 合成知识是否跨局保存、成品图鉴与铁匠配方许可如何区分，以及旧档如何继承。
- 通用材质命名、部位记录、动态染色都不是本次必做项；固定成品是否已足够承载名字与贴图，需要调查。
- “一条武器只改一个部位”是此前探索想法，不得当作必须重构所有路线的硬约束。

先前材料、事件与平衡方案是背景证据，不是本次调查的实施命令。遇到冲突列出旧方案段落及影响，由后续改进方案统一处理。

## 2. 基线、方法与证据标准

1. 读取 AGENTS.md、当前项目状态、架构说明及相关最新报告；记录调查分支、commit SHA、日期、内容导入/引擎版本（如实际运行）。有未合并 PR 时单列，不与默认分支现状混算。
2. 定位真实作者数据、生成资源、加载入口和运行时调用。优先批量导出全量表，避免靠手工挑选几个例子推断全库。
3. 报告每个关键结论给出文件路径、行号或 JSON 键、函数/资源 id；最好提供冻结到调查 commit 的 GitHub 链接。
4. 严格区分：已配置且可达、配置存在但未接通、设计文档中的计划、已废弃/测试专用、无法确认。不得把文件存在等同于玩家可获得。
5. 空字段与不适用写 null/不适用，不用 0 伪装未知。所有统计注明分母、排除项与生成方法。
6. 可参考既有 279、283、292～301 等相关报告及其后续记录，但以最新代码和实际落地为准；不要恢复已取消的设计。
7. 本任务不要求全量战斗平衡实验。静态证据不足的关键流程做最小隔离验证；无法运行则如实标注，不用推测补齐。

## 3. 全量武器与相关道具清单

导出所有正式武器，另列所有合成/打造/升级/任务所引用的相关非武器道具。材料全集可单独成表，避免把所有材料当作已有合成组件。

武器表至少包含：

| 字段组 | 需要的信息 |
|---|---|
| 身份 | item_id、中英文名、类型/子类、稀有度原始值与显示颜色、标签、材质、独特/任务标识 |
| 使用成本 | 占格形状、可旋转规则、重量、买卖价值及推导方式 |
| 战斗定义 | 伤害、冷却、耐力消耗的基础值与单位，伤害类型、攻击/触发方式、核心效果 |
| 属性变化 | 品质、词条、实例字段、局外成长等如何修改三大基础字段；定义值与最终运行值分开 |
| 内容角色 | 独立可用、组件、合成成品、升级中间态、特殊终端等；允许多重身份并给依据 |
| 获取 | 搜索、商店、敌人/Boss、任务、起始装备、合成、局外打造等实际渠道及前置 |
| 资产 | 名称/描述本地化键、图标路径、是否独立图、复用图/缺图 |
| 证据 | 作者数据路径、生成资源、运行时引用与状态 |

相关道具表补充：具体 id 输入与泛材质输入资格、可参与哪些配方、是否有独立使用价值、来源及解锁条件。不要仅凭名字判断“金属”“骨料”或制作资格。

## 4. 完整配方与升级关系图：本次核心交付

将以下关系分开提取，再汇总成图：

- 相邻道具合成。
- 局内设施升级/制作。
- 局外铁匠打造与升级。
- 冶炼、材料转化及其他会影响武器可达性的配方。
- 任务交付/特殊转换形成的武器关系。

每条关系至少记录：

| 字段 | 内容 |
|---|---|
| recipe_id / 类型 | 原始标识及真实入口，不按名称猜机制 |
| 输入 | 每个槽的具体 id 或谓词、数量、稀有度门槛、标签/材质要求、是否消耗 |
| 输出 | item_id、数量、是否固定、品质/实例字段继承或重置规则 |
| 条件与费用 | 解锁、科技、成就、任务、地图、设施、金钱、耗时及其他成本 |
| 空间规则 | 邻接定义、方向、距离、物品形状、是否允许多输入/同类重复件 |
| 触发与结算 | 自动/确认、候选竞争时选择规则、扣除与生成顺序、失败处理 |
| 可达性 | 输入来源与前置是否实际可达，是否只存在于设计文档 |
| 证据 | 数据和生产调用路径 |

用完整输入集合表示配方：A + B → C 不能误画为 A → C 和 B → C 两条可独立完成的升级路径。泛材质槽保留谓词并附合格候选表，不臆造唯一前驱。

按武器家族输出可阅读的路线图与表，标出：

- 起点、分支、合流、终点、链长；链长口径需说明。
- 完全没有合成/升级关系的独立武器。
- 只参与合成、只参与铸造升级、两者都有的武器。
- 同一成品已有多个获取渠道、重复配方、循环或潜在资源套利。
- 失效引用、不可达配方、可用输入为空、成品没有合法来源。
- 每把武器和每件组件关联的配方数量，指出悬浮窗可能过载的项目。

保留完整表，不只给汇总图。配方表行数应与原始配置逐项对账，排除的测试/废弃项附名单。

## 5. 获取渠道与红武唯一性

### 5.1 高阶内容渠道矩阵

为当前金色、红色及其他高阶武器逐件列出真实来源、解锁条件、掉率/权重及其上下文、是否可重复获取、是否可带入/带出。颜色与稀有度映射先查代码，不预设编号。

核查 Boss 是携带后可掉落、专用奖励表、任务奖励还是仅文案提及。暂未存在的 Boss 红武只能记为候选设计空间，不写成现有内容。

检查局外打造高阶成品会不会绕过局内组件收集：需要现有制作费用、材料来源、出征携带限制作为证据，不仅凭稀有度推断。

### 5.2 红武生命周期

查唯一性按 item_id、名称、实例 id 还是任务旗标判断，以及检查发生在生成、领取、入库还是别处。

列明背包、仓库、装备位（若有）、地面、托付、死亡遗留、回购、待领取奖励、战斗掉落缓存等实际存在的位置，追踪移动、丢弃、出售、销毁、死亡、存读档后的行为。

回答：

- 能否同时从两个来源领取同一红武？奖励尚未领取是否占用唯一资格？
- 出售后回购与再次获得是否可能复制？
- 原红武消失后，哪里清除限制？是否被永久任务旗标错误阻止？
- 一次性任务奖励丢失后是否存在重新获取入口？
- 不同具名红武能否共存？旧档重复实例如何被处理？

用户规则与当前实现分别列出；有缺口提供最小复现步骤，不在调查阶段自行定案或修复正式逻辑。

## 6. 合成发现、图鉴与 UI 现状

追踪“物品相邻 → 配方匹配 → 提示 → 预览 → 确认 → 消耗 → 成品生成 → 配方记录”的真实调用链。

分别调查：

1. 成品图鉴解锁条件：看见、拿到地面奖励、进入背包、带出、制造，究竟哪一步触发？
2. 配方知识是否已有独立记录，作用域是局内/存档/全局，是否进入存档。
3. 铁匠配方许可是否与图鉴/合成知识共用字段，解锁方式是什么。
4. 输入武器、组件、成品的悬浮窗目前显示哪些关系，是否提前泄露未知配方。
5. 未知成品的名字、图标、稀有度、属性比较、搜索筛选等是否会泄露结果。
6. 多个合法配方竞争同一物品、满包、锁定材料、取消、重复确认、切场景时怎样处理。

对照以下目标给“已有支持/部分支持/缺失/待决策”矩阵：

| 条件 | 目标 |
|---|---|
| 合法组合，成品图鉴未解锁 | 提示可合成，结果显示？？？，仍显示明确消耗 |
| 合法组合，曾获得成品 | 可查看成品；不因此自动把所有原料配方视为已发现 |
| 首次成功合成 | 记录对应 recipe_id，在相关输入和成品悬浮窗关联 |
| 只看到提示或取消 | 不因未成功操作而误记为首次合成成功 |
| 一种成品有多种配方 | 区分成品已知和每条配方的发现状态 |

图鉴解锁与合成记录的跨局保留、旧档继承若尚无定案，报告现状与选项，不自行写正式迁移规则。

## 7. 属性、命名、资产及存档迁移影响

查明固定成品定义与实例属性之间的边界，尤其是当前升级是否叠加伤害、冷却、耐力、品质或每击效果。列出取消铸造升级后受影响的代码、数据、UI、测试、经济与掉落入口。

需要回答：

- 固定输入 → 固定成品能否直接复用现有系统？哪些实例状态目前必须继承，如磨损、装填、绑定、锁定等（仅列真实存在项）？
- 哪些武器收益主要来自每击触发，不能仅用伤害/冷却估算？
- 具名成品是否已有独立图与文本？是否有必要做材质动态命名或分部位染色？报告成本与现有资产条件，不直接实施。
- 旧档中的已升级武器、旧配方知识、任务旗标、设施状态、品质数据会在哪些位置失去解释？
- 哪些旧方案依赖“每种材质每档都有升级用途”，改革后需要重新审查材料缺口与供应？关联现有材料方案，不能未经审计继续补齐所有档位。

## 8. 工具与最小验证

先列现有审计、配方导出、内容校验、测试夹具和统计工具，逐项说明能否回答本需求。工具存在不等于覆盖上述规则。

必要时写只读导出脚本，复用正式加载/筛选函数；输出中记录命令、commit、数据摘要。不修改玩家真实存档，验证使用隔离夹具。

优先验证：一个现有相邻合成、一个泛材料升级/打造、一个存在多来源的成品，以及红武生命周期和发现逻辑中静态无法确认的关键案例。若需要复杂运行环境，可先交静态证据与未验证清单，不虚构成功结果。

将“实际游戏问题”“调查/测试工具问题”“预期负向用例日志”“未覆盖范围”分开。新增工具运行相应定向检查；纯文档与导出数据不要求无目的地跑全量战斗测试。

## 9. 交付格式与验收

主报告放 docs/reports/ 下下一可用编号，建议题名“武器、合成与铸造升级现状调查”；附表/脚本遵循现有目录惯例，全部使用相对链接关联。交付至少包括：

1. 主报告：基线、主要发现、机制调用链、目标支持矩阵、问题与未决项。
2. 全量武器表与相关道具表：CSV 或 JSON，主报告提供便于阅读的摘要。
3. 全量配方/升级关系表，以及按武器家族拆分的路线图。
4. 高阶武器获取渠道表与红武唯一性生命周期表。
5. 现有工具覆盖表、必要复现证据、导出命令与覆盖对账。
6. 改革影响清单：可直接复用、需调整、小型新增、风险较高四类；复杂度依据具体改动范围说明，不编造精确工期。

报告最后回答这些决策问题：

- 当前有多少武器、多少真正可用合成/升级配方？覆盖哪些家族？
- 若取消铸造升级，哪些武器/材料/任务会立即失去用途或来源？
- 哪些现有组合最适合保留为少量特色合成？哪些只是数值阶梯？建议与事实分栏。
- 哪些武器已有条件做双渠道，哪些值得局内限定？给来源依据，不最终改表。
- 用户提出的发现规则与存档唯一规则，各自最小需要修改哪些模块？
- 哪些问题必须由用户决定，哪些可以在后续方案中按现有规则实施？

验收要求：全量原始数据可追溯、数量能对账、所有武器有关系分类（包括“无关系”）、无法确认项显式标记。不要只交一段总体评价，也不要提前提交一套新武器数值表。

更新报告索引；status 仅记录调查交付与待办，不能标记改革已完成。按用户既有约定提交、推送、创建 PR 并合并默认分支，遵守分支保护与必需检查。最终回复提供报告链接、调查 commit、主要阻塞点及未覆盖范围，供后续编写改进方案使用。
