# 合成、局外打造与武器来源改革：基于调查 304 的执行方案

> 日期：2026-11-11。供 Claude 分批实施。本文合并仅表示方案交付，不表示玩法改革已完成。
> 依据：[调查 304](../reports/304-weapon-fusion-forge-survey.md)、[完整证据目录](../reports/research/evidence/2026-11-11-weapon-fusion/)、用户最新讨论。
> 调查基线 main@254f084c，Godot 4.7.1；执行时重新导出最新默认分支并报告差异。旧报告不覆盖，后续另写实施与测试报告。

## 1. 目标和范围

局内采用少量、固定道具组合的相邻合成；局外铁匠铺负责已解锁配方的材料打造。取消普遍的武器逐阶升级，不把 82 条旧升级逐条平移为 82 条合成。

固定配方产出固定武器定义，不新增伤害、冷却、耐力随机浮动，不做通用部位改名系统。现有武器 id、独立贴图和中英名字优先复用，避免因为入口改革删除玩家成品。部分高阶武器允许双渠道，部分仅局内合成；未列入合成的武器保留独立使用价值。

本文中“建议初值/候选”用于实施实验，不冒充用户已逐件确认的内容定案。没有完整来源替代表和存档验证，不关闭旧入口。任务红武剧情留白不在本轮擅自补全。

## 2. 事实、证据限制与纠错

| 调查事实 | 对执行的影响 |
|---|---|
| 120 个作者武器定义，包含 8 个本体红武和 8 个同名 lesser；不含 312 个运行时赐福异体 | 不是 120 把全部正常可得，更不是 16 把独立唯一红武 |
| 124 条配方：14 相邻、9 拖合、82 升级、17 打造、2 冶炼 | 相邻与拖合应共用发现/结算规则；升级退出不等于删除全部制造 |
| 17 把元素金武 + 帝国佩剑具有 forged_only，依赖升级 | 18 件必须逐件接入新来源才能关闭旧升级；不能全局删 forged_only 让它们进普通商店 |
| 当前产物有独立图和双语名字，描述为空 | 优先复用，不强行新增道具描述或动态染色 |
| 86/120 武器每击有附加效果 | 不能仅以伤害/冷却判断组合收益和品质变化 |
| 小锤按下即消耗，无确认；合成不记录 recipe_id，也不立即点图鉴 | 先补安全结算、发现状态与预览，再扩内容 |
| 砧和铁匠共用升级；砧不读级数/科技 | 移除砧不是小 UI 调整，会改变早期高阶装备可达性 |
| 红武本体目前正常流程均不可完整取得；Boss/猎手掉的是同名 lesser | 新 Boss 红武不是已有内容换一个来源开关，需独立内容与唯一性迁移 |

**材料数量纠错**：304 §五.2、§十建议有“两颗/三颗魔晶石”的表述。当前 `SmithRecipeDef.material_inputs` 的值是最低稀有度、每类一件；`{"crystal:fire":3}` 表示一颗紫或以上火晶，`{"metal":4}` 表示一件金档或以上金属。已核对当前 `core/meta/smith_recipe_def.gd`、`core/run/anvil.gd` 和 `anvil_flame_fang.json`。数量只有 `inputs` 中的数值表达，不能混读。后续新增泛材料数量需独立字段。

**证据限制**：verify.log 只复现“寂灭已在地上但献祭条件仍成立”，未证明完整任务链正常可达、也未完成实际第二件生成的端到端验证。报告“输入可达”多为候选资格，不能替代路线概率实测。日志资源泄漏警告另列工具问题并查明，不默认为所有测试通过。主报告比附表中的“全程静态”描述更新，逐项按 verify.log 判断动态覆盖。

## 3. 交付次序

| 批次 | 产物 | 合并/启用条件 |
|---|---|---|
| A 可靠性与知识状态 | 锁定检查、统一确认/结算、成品可见性、配方发现记录、存档测试 | 不改武器数值、不删除旧入口；知识规则已在所有合成入口一致 |
| B 来源与配方清单 | 全量 82 条升级处置表、18 件金武来源表、打造需求表、少量合成候选 | 无遗漏、无将门槛误作数量、无无意断供 |
| C 有限合成与材料打造 | 固定组合与新泛材料数量支持，来源补齐 | 实际生成/领取/合成/存读档走通；首轮经济对照完成 |
| D 关闭旧升级 | 取消局内砧升级和局外升级配方入口，清理提示/科技文案 | B/C 的来源与旧档门禁全部通过；附魔炉等无关功能继续正常 |
| E 红武体系 | 独立 Boss 身份、出售与重获、旧 lesser 迁移 | 独立完成命名/来源/旧档决策后启用；不阻塞普通合成改革 |
| F 联合验收 | 地图供应、构筑、发现 UI 与经济报告 | 新旧版本对照、未覆盖清楚，更新状态和架构 |

A 可先做；B 完成前不批量新增材料或改稀有度；D 不能先于 C。E 中独特机制/剧情未定的内容保留待办，不凭本计划恢复被作废的任务链。

## 4. 相邻合成的范围与候选

### 4.1 保留基线与控制规模

- 现有 14 条相邻配方先原样保留输入/成品，作为基线；并非所有输入都是白色，磨刀石与鞣革等为绿色。
- 9 条拖合配方保持 recipe_id 和内容，迁为相邻交互，共用一次确认流程；不同时保留“松手直接吃物”的旁路。包括 poisoned_knife 和八条生存道具组合，不把它们漏出发现系统。
- 迁移前提供可用背包格不足时的操作验证，确认拖合用户不会失去原先可完成的组合。教程、中英帮助和拖拽反馈同步更新。
- 首轮新增高阶候选控制在 4～6 条（建议预算，不是永久上限）；不追求所有家族全覆盖。现有独立武器不强加后继，不加“每局合成次数上限”。
- 同一对无序输入只对应一条配方，出现冲突导入报错，不按文件顺序暗选。一个输入可能邻接多个伙伴时，让玩家明确选择要消耗的两个实例。
- 单条配方首轮仍为两个具体实例，每种一件；knife + knife 必须消耗两个不同 uid。不新增任意数量的局内多件匹配。

### 4.2 第一轮具体候选（实验，不一次性铺满）

以下均为已有 id 组成的建议；成品保留现有机制，先检验可达性和强度。新 recipe_id 独立命名，记录对应旧升级的退出关系。

| 两件具体输入 | 成品 | 建议来源定位 | 要验证的问题 |
|---|---|---|---|
| cleaver + beast_fang | bloodletter | 合成 + 局外打造 | 兽牙供应、放血效果是否值得消耗；已有 smith_bloodletter 可作为打造改造起点 |
| shortbow + antler | horn_bow | 合成并保留既有合法随机来源 | 角材叙事合理；不因新增配方擅自变成仅合成 |
| steel_crossbow + hardwood_plank | heavy_crossbow | 合成 + 局外打造候选 | 固定木材而非任意骨/木二选一，测试装填格与成品尺寸 |
| bloodbone_spike + fire_crystal | flame_fang | 局内合成限定候选 | 紫色具体火晶一颗，不接受任意高阶替代；原武器来源必须实际可达 |
| bloodbone_spike + ice_crystal | frost_fang | 局内合成限定候选 | 同起点的两种方向，不强求整条匕首路线可合成 |
| heavy_crossbow + lightning_crystal | thunder_heavy_crossbow | 局内合成限定候选 | 两步短链作为上限观察样本，别让所有金武照此复制 |

成品选择理由是主题与分支辨识度，不以“金色更高所以必然更好”作为论证。输入实例附魔/成长等损失见 §6，不能静默覆盖。

### 4.3 82 条旧升级逐条处置

基于 recipes.csv 生成版本化 migration_manifest，至少包含 old_recipe_id、完整输入与门槛、output、处置（替换合成/改为材料打造/保留其他来源并停用）、新入口、新配方、解锁、旧 id 兼容、实测证据。

同成品多条旧升级可以合并到一个打造配方，不需要保留骨→金属、金属→骨两条相同终点。蓝紫武器的随机来源资格先保留并测试，不能把“旧升级无用了”误判为武器应删除。

18 件金武建议分流：上述 flame_fang、frost_fang、thunder_heavy_crossbow 先试局内限定；其余 15 件优先评估直接材料打造，少数后续再转 Boss 专属。每件都要有实际来源，不能仅写“未来 Boss 掉”。大魔导杖已有多来源，不随本批改变成 Boss 专属。

这是来源分配起点，B 批必须生成完整 18 行的材料数量、解锁与经济表后才实施。不沿旧升级递归展开所有前驱材料照单相加，那会把旧长链成本伪装成一张巨额配方。

## 5. 局外铁匠铺：材料打造而非另一套升级

### 5.1 需求结构

复用 SmithRecipeDef 与正式导入/生成资源管线；为泛材料需求补明确的 material/family、min_rarity、count。保留精确 id 输入用于具有不可替代功能的组件与冶炼，不将科技、任务物品当普通材料自动消费。

旧 material_inputs 通过兼容转换解释为 count=1，min_rarity=旧值；不要原地改成“数值代表数量”。导入拒绝 count≤0、未知材料家族及无候选需求。

匹配应输出具体 uid 分配表：一个实例不能同时满足精确输入与泛材料槽、也不能满足两个重复槽。重叠候选采用能找到可行解的匹配方法，不能因贪心先占稀缺材料导致“明明够料却不可打造”。

UI 预览实际要扣的件，默认优先低档且未锁定的合法材料，允许调整；确认时重算合法性，材料变更则刷新预览，不悄悄换扣更贵材料。资金与容器容量也参与同一事务。

### 5.2 打造与权限

- 普通武器打造逐步改为材料需求，不再消费“上一把武器”。现有 smith_mithril_sword、smith_grand_magus_staff 虽名为打造，也含前驱武器，必须纳入迁移。
- 冶炼两条及防具/盾的制造继续存在；具体需求可泛化但不误删。
- 配方许可首轮沿用设施/科技，显式区分可打造与仅合成。不因获得成品图鉴就自动取得铁匠许可，也不因打造而自动发现局内组合。
- 直接打造高阶品需核算材料份额、资金和解锁；与旧 60/120/200 升级费不能机械等同。第一局/新档和成熟仓库分组测试，不能靠新增无依据时间门槛修补。
- 双渠道产物使用同一 ItemDef，来源本身不提供隐藏战斗加成。

### 5.3 品质策略：本轮建议及兼容

局内合成继续固定品质 0，无随机或按材料阶级加成。为符合“符合材料门槛即可打造指定成品”，新材料打造也建议固定品质 0；高档替代只满足资格，UI 明示不提升成品品质。

这是新制造规则建议，不把用户已认同的固定合成结果扩大解释成“允许清空所有旧品质”。旧武器 quality 及其战斗作用保留，不重写存档。用旧 q0/q1/q2 与新 q0 分组做战力与价值对照，尤其每击效果；达不到合理成长收益时调整新来源成本/配方内容，不偷偷全局削弱敌人。

若实施阶段选择保留局外材料品质差异，必须作为独立实验明确写入修订方案，不能一边宣称双渠道同值一边继续静默加品质。

## 6. 预览、发现、消耗与保存

### 6.1 三类知识分离

建议增加存档级 discovered_fusion_recipes，按 recipe_id 持久保存。已有成品图鉴/物品认识与铁匠科技许可各自独立。首次成功合成才记录对应配方，取消、预览、获得成品、铁匠打造不记录其他合成配方。

用户要求“曾获得成品则能看”，但现有 codex 主要在带出时计数且参与计分/成就。建议新增 seen_item_ids 作为图鉴认识集合：实际入玩家背包/仓库或成功制造时记录；只看到敌人/商店商品或未拾取掉落不记。图鉴可展示“已认识但未带回”，原有带出/收藏计数不虚增。成功合成落在地上的成品也已被制造者认识。

不要为显示预览而反复调用增加 codex 件数的接口。旧档从 codex>0 和真实持有物品初始化 seen，不从全部配方反推 discovered；旧配方 id 重命名用明确别名映射，不能从“有一把成品”猜已合成过全部来路。

### 6.2 UI 状态表

| 条件 | 相邻提示/确认 | 普通物品悬浮窗 |
|---|---|---|
| 配方未发现，成品未认识 | 可合成；两件明确消耗；成品为统一未知图标与？？？ | 不列出未发现组合 |
| 配方未发现，成品已认识 | 可合成；显示真实成品与比较；仍需确认 | 不因成品已知泄露所有配方 |
| 配方已成功发现 | 显示成品和消耗 | 两个输入显示“可与 XX 合成 YY”；成品显示“由 XX 与 YY 合成” |

未知预览不泄露名字、稀有度颜色、图标轮廓、精确成品属性、配方链接 note 或隐藏 tooltip。保留玩家已知的输入损失信息；旧 reveal_names 设置不能无意绕过新规则，默认不对合成结果生效，若保留剧透模式须明确命名且不改知识状态。

在小锤上点击先开预览，再确认；确认前可取消。现有反向链接、百科、子窗、拖拽提示、已知物品跳未知物品均走同一个可见性策略。悬浮窗最多先列少数已发现且相关的关系，其余展开；不要把未知配方总数作为必需提示。

### 6.3 事务与实例规则

执行入口重新检查两个 uid 存在、仍相邻、未锁定、非受保护件、配方匹配、结果容器可接收。先计算落点与状态，再一次提交；失败不扣物、不记配方、不点亮知识、不加合成次数。满包走既有落地兜底并明确提示。

新件沿既有规则重新生成 uid；首轮固定品质 0、磨损/消耗次数按成品定义初始化，附魔、成长、法杖进出局计数不自动继承。确认窗明确列出会丢失的输入状态；未知成品也可说明输入上的附魔/成长将消失，但不揭示成品字段。不能泛拷贝 state。

物品消耗/生成、统计、知识记录与保存需具备崩溃一致性。当前 run/meta 分文件保存，不能只“调用两个 save”就宣称原子；先复用既有事务设施，没有则用最小交易日志/提交标识实现恢复和幂等。测试在两次写盘之间中断，必须恢复到完整提交或完整未提交；重复恢复不增物、不重复计数。旧砧在关闭前的临时槽保存风险单独复现修复，不能因将来删除而忽略。

## 7. 来源门禁与旧存档

D 批关闭升级前，自动检查：

1. 82 条旧升级逐条有处置，18 件金武逐件有替代来源与验证；旧 baseline 120 是调查数字，最新库增量另列。
2. 仅合成标记与实际源过滤一致：搜索、普通敌人、商店、集市、事件池、信仰赠物、铁匠不能漏出限定物。forged_only 语义可迁成明确来源策略，但不得全局放开。
3. 留下的物品 id、图、科技与库存可加载，旧品质/附魔/成长不因改革被抹除。删除配方本身无需给所有物品改 id。
4. 存档中 used_anvil 可兼容读取并忽略；已打开砧临时槽的输入/成品安全归还，不能依赖旧 UI 持有未保存物。
5. 只关闭 Anvil 升级服务，不连带删除 Forge 附魔、休息恢复、神坛、寂灭法杖计数或法杖装填。
6. 旧界面“可升为”、升级设施说明、科技描述和教程无死链接；打造比较和合成比较复用有价值的部分。
7. 材料用途重算；原材料方案中“补齐所有升级档位”的理由不再有效。绿木、绿石是否仍需新增由新配方决定，已有物品不直接删除。

事件奖励池仍按既定不耗尽主题池执行；只能更新候选用途和权重，不能为补合成材料把它改成有限库存。

## 8. 红武与 Boss 来源独立批次

### 8.1 统一身份与唯一性

用户已明确同一红武每存档一件、不同任务/Boss 武器名字不同。以稳定 identity_id（无异体可先沿 item_id）判断，不用本地化名称比较；旧 lesser 同名不等于允许沿用其非唯一规则。

所有新来源在生成/领取提交时复查同一唯一性服务，包含本局和局外实际可取回容器。先补寂灭条件的 run 扫描及执行端检查；不用补冰/毒章节来掩盖检查缺陷。测试地面、托付、其他节点、尸体和待领取等位置，以及两个奖励同时提交。

建议边界：仍可捡回/回购的原实例占唯一资格；真正销毁、远征结束遗留丢失、不可回购出售才释放。允许出售红武应只针对红武而非所有 unique 任务物；出售可采用不可回购确认规则，或回购期保留资格，两者不能混用。本方案默认建议红武出售不可回购，确认文案明示，完成后允许重新获取；这是待内容批次验证的流程选择，不是当前游戏已支持。

### 8.2 当前 lesser 与新 Boss 内容

不能将八个 lesser 批量加 unique：旧档可能已有多件，会直接违反新规则且可能吞玩家资产。先列逐 id 迁移表：旧名称/实例数、新身份、稀有度、显示名、允许来源、旧实例处理。

建议旧 lesser 转为有独立名字的普通金色遗物候选，保留 id 和实例，比较其真实强度后决定是否适合金档；若不适合，不为了改颜色直接削弱旧物。真正 Boss 红武使用独立 id、名字、机制和专属 Boss 来源。迁移未定前不启用新红武体系，也不把八个旧 lesser 偷偷当已完成的新 Boss 红武。

新增 Boss 首轮只做小规模具名设计。每件需给 Boss 实际 id、章节、胜利条件、掉率/保底选择、唯一重复时的替代奖励和中英文名字；这些尚无定案，先提交内容表，不虚构任务世界观。Boss 奖励分布需把持有率与胜后掉率分开统计，不能把它们混成最终概率。普通 Boss 金保底目前偏 treasure，不会自动给金武，专属武器要明确接线。

### 8.3 任务链边界

破晓信物重复取得与 npc_done 写入时机独立修复：成功给物后才标记领取；丢失后允许按指定恢复规则重拿，保留剧情完成记录。只修入口可靠性，不擅自编写破晓后续、补冰/毒章节或恢复已作废链条。寂灭现不可达必须继续标注，不能声称新红武方案使所有任务红武可得。

旧档若发现同身份多个真正 unique：备份并输出冲突清单，暂停新增该身份的奖励，提供明确迁移选择；不静默删掉多余实例。
