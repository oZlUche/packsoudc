# 平衡检测、统计与胜负感知：Claude 执行指导方案

> 日期：2026-11-10。
> 依据：当前仓库源码静态核对、报告 242 / 245、既有平衡报告及一名玩家的反馈。
> 玩家反馈原文：**「对于胜负没有实际感受」**。
> 本文是待执行方案，不是工具实现或测试通过报告。工具名标为“新增建议”的均尚未实现。
> 与 `2026-11-09-claude-next-execution.md` 配套：本文细化其平衡与诊断部分；未完成此前稳定性检查时，先建立测试基线。

## 1. 执行目标与边界

本轮交付可运行的检测、统计和诊断工具，用有限真人反馈定位问题。优先级依次为：数据可信 → 单场可复现 → 分布统计 → 胜负感知诊断 → 对照实验 → 整局经济压力测试。

第一轮不自动大面积调参、不增加正式玩法、不直接加重失败惩罚，也不把视觉特效增多当成反馈问题已解决。实现诊断工具、测试夹具和离线报告；体验改动先形成有证据的小实验，再决定正式方案。

开始时读取适用仓库规范，记录 HEAD、引擎版本、工作区改动。所有路径相对仓库根目录，示意接口需结合实际类名落地。复用生产逻辑，保持 core 不依赖 ui；不要另写战斗规则或经济规则。

## 2. 现有工具是否满足：源码审计结论

结论：**现有能力适合初步扫表，不足以独立支持精确归因、版本对比和玩家体验判断。应增量扩展，不能推倒重写。**

其他确认：`ui/game/battle_screen.gd` 已接倍速、跳过及最终胜负展示；不能声称游戏完全没有反馈。应调查这些反馈实际出现的时机、玩家看到了多久，以及是否能理解。

## 3. 将“胜负没有实际感受”拆成可验证问题

这是一名玩家的一条真实质性反馈，不是总体满意度统计，也不证明游戏必然太简单。尚不清楚他说的是单场战斗、整局结算还是两者。

| 假设 | 需要观察的证据 | 可做的最小对照实验 |
|---|---|---|
| A：不知道为什么赢或输 | 玩家能否说出关键道具、伤害来源和失败条件；日志是否支持其理解 | 同一回放，有无一条基于事实的关键事件提示 |
| B：认为自己的准备没有影响 | 合理换装或摆放后，结果和过程指标变化；玩家能否预测变化方向 | 同敌人、多种子，替换一个可获得组件或改善一次摆放 |
| C：战斗没有起伏或来不及看 | 模拟时长、血线、有效出手次数、展示墙钟时间、倍速与跳过记录 | 相同战斗结果，正常速度和现有默认速度分组呈现 |
| D：输赢后的损益不明显 | 战前后资源变化、玩家能否说出得失、下一步选择是否变化 | 相同奖励与损失，只改变结算信息的组织方式 |
| E：对手看起来一样，重复战斗无意义 | 相邻战斗的敌人类别、构筑、威胁、结果过程是否高度重复 | 选择机制明显不同的既有敌人做短场景体验 |
| F：失败看起来不可控或随机 | 同配置换种子的差异、调整策略后的变化、可观察的预警 | 并列展示两种合法准备方案及种子分布 |

不要生成一个“胜负感得分”替代这些维度。机器统计只能提示风险；真正的感受必须由人报告。

若能联系该玩家，请作者用三问补充，不阻塞工具开发：① 指单场还是整局？② 更接近看不懂原因、感觉装备无影响，还是输赢无所谓？③ 当时版本、倍速及是否跳过？本任务不自行向玩家发送消息。

## 4. P0：数据契约与完整性审计

### 4.1 新增公共实验元数据

在校准模块内建立轻量公共格式，建议新增 `experiment_manifest.gd`，沿用现有 JSON / JSONL。至少包含：

```json
{
  "schema_version": 1,
  "experiment_id": "本轮唯一标识",
  "source": "synthetic",
  "build_id": "提交及未提交改动摘要",
  "engine_version": "实际版本",
  "content_hash": "规范化输入内容摘要",
  "suite_hash": "场景与配装集合摘要",
  "seed_manifest": "seeds.json",
  "config": {},
  "started_at": "UTC时间"
}
```

`source` 明确区分真人、作者、自动策略与合成战斗；不要把合成行拼进真人统计。存档延续的 run_id 应持久化，重复导出保留相同 battle_id / event_id；新开同种子局仍有不同 run_id。模拟实验另外使用 case_id、pair_id、replicate_id。

构建标识由构建或开发启动阶段注入，玩家包运行时不依赖 Git。内容摘要包含实际影响实验的资源与配置；未提交修改不能仅以 HEAD 代表。格式版本与游戏版本分开。

### 4.2 检测工具（新增建议）

`tools/audit_balance_data.gd`：读取目录或导出包解压目录，输出 `audit.json` 和 `audit.md`。

检查：文件缺失、坏行、未知 schema、重复 id、同 id 不同内容、跨版本混合、缺字段、非有限数、无效种子、无法加载道具、非法布局、记录链缺口、请求场数与实际场数不符。

旧数据允许分析已有字段，但输出 `reproducibility=approximate/unknown`；不补造 run_id 或战斗上下文。缺失指标写 null 并给出原因，不能用 0 冒充。

版本混合默认分组输出；显式 `--allow-mixed` 才允许额外混合视图，并加醒目标识。提供 `--build`、`--chapter`、`--character`、`--source` 等过滤参数。

### 4.3 验收

- 夹具包含坏 JSON、重复导出、同种子不同局、旧格式、未知格式、缺失值、两个构建混合。
- 输出输入总数、有效数、去重数、排除数和原因；数量能对账。
- 严格模式下严重损坏或混合拒绝退出码 2；通过但存在分析警告仍在报告中列明。退出码含义写入使用说明。

## 5. P0：精确战斗诊断输入与复现

### 5.1 实现路线

在实际调用 `BattleSim.run` 的边界捕获只读深拷贝，而不是从结果页反推输入。先追踪所有正式战斗入口和随机数消费路径。

诊断包保存：双方完整有效战斗输入、实例状态、规则参数、时限和加时规则、模拟开始前 RNG state/seed、构建及内容摘要、场景元信息。如果 CombatantSpec 无可靠序列化，应为诊断实现版本化编码器，或保存足以重建全部 CompileInput 的输入并验证等价；选择一种主路径，避免同时维护两份不一致事实。

不要把现有回放格式直接改成不兼容格式。诊断包可作为同 stem 的附加文件，离线复现实验不执行结算、不修改真实存档、不触发正式经济奖励。

新增建议 `tools/reproduce_battle.gd`：加载包，在匹配构建下重跑，比较 winner、duration、关键最终资源及规范化事件摘要；不一致输出第一个差异位置。旧包缺上下文时拒绝宣称精确复现，允许仅播放原回放。

RNG 注意：当前 matrix 将敌人选择、组装和战斗依次使用同一 RNG，只有初始种子不足以独立重放战斗。记录开始模拟前的状态；对照实验固定敌人实例及战前 RNG。修改规则后随机调用次数可能改变，所以同种子不保证事件逐项对应，结论依赖多种子分布。

### 5.2 开销与导出

完整包优先用于开发实验及明确的诊断采集模式；普通记录保留轻量摘要。测量捕获、序列化、线程写入的耗时和体积，给出保留数量与容量上限；反馈固定导出不受 200 场滚动清理影响。写盘失败不影响游戏，报告诊断覆盖缺口。

### 5.3 验收

普通武器、状态伤害、信仰、局外加成、道具品质及耐久、特殊角色各至少一个确定性场景；保存重载后结果与事件摘要一致。坏包、缺资源、构建不匹配均有明确错误。验证不会推进正式存档或二次结算。

## 6. P1：逐场统计与实验报告

扩展现有 matrix，新增纯计算模块（建议 `battle_metrics.gd`、`balance_statistics.gd`），让猎手和真人日志分析复用；避免在 UI 中统计。

### 6.1 逐场记录

每个 case 至少写：case/pair/replicate id、来源、双方配装标识、角色、进度段、预算口径、敌人类别、实际敌人实例摘要、抽样模式、种子与 RNG 状态引用、胜败/平局/超时、模拟时长、双方最终血量、数据有效性。

每次生成失败也写一行 error case，包含原因。报告同时显示 requested、generated、simulated、valid、failed；缺失 case 不计作战败，也不能静默丢弃。全失败不是 0% 胜率，而是无有效结果。

输出目录建议：

```text
<output>/<experiment_id>/
  manifest.json
  seeds.json
  cases.jsonl
  summary.json
  summary.csv
  report.md
  diagnostics/              # 只保存异常或抽样的完整包
```

大批原始数据留外部产物目录；Git 中提交小型夹具、配置和摘要报告，禁止把真实玩家原始数据直接提交。

### 6.2 指标定义

| 指标 | 明确定义与注意点 |
|---|---|
| 胜率 | wins / 有效模拟场数，平局另列；纯胜率与平局折算得分不得混称 |
| 不确定性 | 独立合成重复给 Wilson 95% 区间；固定穷举集合的结果标为该集合表现；真人数据按局/玩家聚类，不能把同局每步当独立玩家 |
| 时长 | 全场及按胜/负/平局分别给 p10/p50/p90；标注样本数与分位数算法 |
| 余血 | 双方分开、按结果分层；仅胜利余血不能代表整个难度 |
| 有效出手 | 两侧各道具实际触发次数；未完成一次有效出手的场次比例 |
| 耐力压力 | 只有能观测真实阻塞时才计算“因耐力不足错失的出手”；仅凭耐力低不得断言停火原因 |
| 伤害来源 | 依据实际扣血事件归属，不重复累加触发链；区分直接、持续、真实伤害；无法归属列 unknown |
| 过程紧张度代理 | 最低血量、低血时间、首次有效伤害时间、首次低血时间；不称为玩家紧张感 |
| 平局与异常 | 超时、无进展、异常终止、组装失败各自计数，按引擎实际终局原因归类 |

不要仅根据生命百分比交叉声称“胜势反转”：双方防御、输出与护盾不同。可以画血线并标注事实事件，但胜率随时间的变化需要另一个经过校验的预测模型，本轮不做。

### 6.3 抽样与比较

- 覆盖测试：显式枚举敌人身份与档位，寻找极端克制。
- 频率测试：按生产选择条件与权重抽样，需包含真实节点/章节上下文。
- 两种报告分开；普通 battle 假节点扫表不能命名为真实地图难度。
- 配对比较固定 case、敌人实例和种子集合；输出差值及配对 bootstrap 区间。真人样本按局聚类。
- 初筛每格 100 场可沿用，不能据 52% 对 48% 宣布强弱。需复核时预先确定追加样本量，避免反复试到显著。
- 训练种子与验收种子分开，参数调好后在留出集合验收。
- 告警阈值写配置，标为筛查值而非作者定案。大量扫描的异常排名是探索结果，应在新种子上复核。

### 6.4 验收

构造全胜、全负、全平、单样本、零样本、极端长尾、缺失事件、重复样本、生成失败夹具。统计结果与独立手算小样本一致；Markdown/CSV/JSON 来自同一 summary，不各算一遍。

## 7. P1：参考配装与合法性检测

扩展现有 ArchetypeBuilder，不重新生成整套体系。场景清单分为合理配装、常见失误、优化上限；按角色、进度段和核心机制覆盖。无需一开始穷举所有维度。

新增建议 `tools/check_balance_scenarios.gd`，验证所有道具存在、占格/旋转/包覆盖合法、独一限制、材料及升级条件、预算、重量；检查指定核心道具确实放入，生成器丢弃物品不能静默算完成。

预算同时记录格子、重量、购买/制作投入和获取前提。不采用待校准的 PowerEstimate 作为唯一等成本定义，避免循环论证。

每份场景记录目标和失误类型，例如“移除回复件，测试耐力依赖”；不存在真人数据时标签只能写 synthetic，不写“普通玩家平均包”。真实木桩按局均衡抽样，保留多个代表及来源，不只保留 HP/DPS 中心。

验收：相同场景和种子生成一致；所有违规输入明确拒绝；每个失误对照只改变声明因素，无法单因素实现时列出连带变化。

## 8. P1：胜负感知专用诊断

### 8.1 两条时间线必须分开

战斗结果来自模拟；玩家看到的是回放。分别记录 simulation_duration 与 presentation_elapsed，后者扣除暂停、后台失焦时间；记录速度切换、跳过时刻、结果揭示时刻和离开界面时刻。缺少历史 UI 记录时不可从模拟时长推算玩家观看时间。

在 `ui/game/battle_screen.gd` / `ui/battle/battle_view.gd` 加轻量会话事件，经现有装配层写入诊断记录，战斗 core 不引用 UI。可记录关键提示的显示与停留，但停留不等于阅读或理解。

### 8.2 离线诊断报告（新增建议）

`tools/battle_experience_report.gd` 关联 battle_id、播放会话和战后状态，输出：

1. **原因可见性证据**：主要实际伤害来源、关键状态/耐力事件、这些事件在显示时间轴上是否集中到很短窗口；不强行给唯一胜负原因。
2. **准备有效性**：一个可获得组件或一次摆位改动，在配对多种子下如何影响结果、余血与时长。
3. **过程节奏**：有效出手数、双方血线、第一次有意义的交互发生时刻、跳过与倍速记录。
4. **后果差异**：战后实际体力、物品、钱、进度变化及展示内容。区分单场战果、整局结果和 UI 已显示字段。
5. **未知项**：无法复现、没有 UI 记录、缺战后状态等，不能留空后默认为正常。

事实归因与因果推断分开：伤害最高的物品不一定是取胜关键；控制、回复与防御可能决定结果。移除一件后的差值称“该条件下的边际变化”，不是可相加的全局贡献。

### 8.3 最小人工验证

准备 6～8 个短场景，覆盖：碾压胜、明显败、接近胜负边界、耐力不足、克制、一次合理换装后改善，以及战后有明显得失的情况。所有场景保存输入包与预期事实。

让作者或愿意反馈的玩家回答：

- 你认为刚才为什么赢/输？
- 哪个准备选择有帮助，下一次会改什么？
- 这场之后你具体得到了/失去了什么，影响下一步吗？
- 对原因的清晰程度与结果的重要程度分别打分，并解释原因。

先自由回答再展示诊断，不在问题里暗示正确答案。标注作者/玩家、样本数和既有熟悉程度；同一人看 A/B 会有学习效应，使用等价不同场景或交错顺序。小样本仅用来判断具体理解障碍，不宣称总体满意度提升。

### 8.4 根据证据选择后续改动

- 原因不清：试验一条可追溯关键事件摘要，不直接做铺满屏幕的数据面板。
- 准备无影响：检查伤害/防御阈值、组件失效、配方获取成本；先确认不是测试没覆盖正确机制。
- 过程来不及看：先对照倍速与提示时序；不直接把所有敌人血量翻倍。
- 后果看不见：先改信息表达；若得失本身无关紧要，再讨论经济和风险设计。
- 随机压过决策：比较配置差异和种子差异，再讨论降低随机或增加可预判信息。

本阶段验收是可复现实验与诊断报告，不是工具打印“胜负感已改善”。

## 9. P2：敏感度、极端组合与整局经济

### 9.1 敏感度与组合搜索

新增建议 `tools/bench_sensitivity.gd`：基线与单因素变体使用固定 case 集，先在实验输入副本上调整，不直接改正式 JSON。连续量可从 ±10% 试起，整数/阈值采用合法相邻档；记录实际值。

新增建议 `tools/search_builds.gd`：从合法参考配装出发做局部替换和摆位搜索，预算与获取限制固定；多目标保留胜率、占格、成本和弱点。搜索集合与验收集合分离，结果只能称可达到的上限，不能视为典型玩家。

最小验证：人工放入已知强组合应被发现；非法布局和不可获得条件不得混入；记录所有搜索预算，避免无限运行。

### 9.2 先经济流水，再整局策略

通过实际交易、合成、带入、托付和结算提交点记录资源 delta，统一 event_id / run_id。每笔包括原因、前后余额、物品实例变化、系统生成/消耗项；交易撤销与失败不得写成成功事件。

新增建议 `tools/economy_report.gd`：对账期初 + 流入 - 流出 = 期末，金币、物品和材料各自记账；物品估值变动与真实现金变化分开。制作消耗与生成按配方对账，不要求物品件数机械守恒。

然后才考虑 `tools/bench_run_policies.gd`：保守撤离、深入搜索、构筑优先、有限常见失误四类策略，调用真实 GameFlow / RunState 行为，记录可用动作和选择原因。策略只能读取玩家当时可见信息，禁止偷看未揭示节点或未来 RNG。

同地图种子比较不同策略，输出原因分类、资金、升级时机、撤离结果和下一局起步条件；标为“策略压力测试”，不称真人撤离率。先支持一张图的有限动作集，明确未支持分支；未实现动作不能悄悄跳过。

## 10. 实施批次、依赖与交付

| 批次 | 内容 | 完成门槛 |
|---|---|---|
| A：可信输入 | 数据契约、审计器、版本过滤、精确诊断包和复现器 | 旧数据可读且标注限制；新包能复现；失败不污染存档 |
| B：可信统计 | 逐场输出、合法场景、公共统计、matrix/猎手接入 | 请求/失败/有效数量对账，分布与区间正确，报告可追溯 |
| C：解释反馈 | UI 时间线、胜负过程报告、单因素配对、小型人工场景 | 能区分原因不清、准备无效、节奏不足与后果不明；未知项明确 |
| D：扩大检测 | 敏感度与极端组合搜索 | 在留出样本上复核，未修改正式平衡数据 |
| E：整局压力 | 经济流水与报告，然后有限策略模拟 | 对账通过、无隐藏信息作弊、不冒充真人体验 |

**第一批实际执行范围是 A～C。** 不要为了等待真人反馈停下数据和工具工作，也不要先花大量时间建设整局 AI 玩家。

每批新增必要的小型确定性测试，优先扩展 `test_calibration.gd`、`test_balance_242.gd`、`test_assumptions_245.gd`、`test_battle_trace.gd`；复杂新模块可独立测试。修复及工具完成后运行定向测试，再跑全量 `bash tools/test.sh` 和 `bash tools/warnings.sh`，保存实际结果。

性能验收报告需比较开启/关闭诊断的模拟耗时、界面捕获耗时、输出体积和峰值内存；不凭感觉宣布“无性能影响”。先给基线与增量，再设合理门槛。

最终交付：工具说明与真实命令、版本化 schema、小型测试夹具、一个完整样例实验目录、数据质量报告、当前版本统计、针对玩家原话的诊断报告，以及按证据排序的后续修改建议。

报告按 `docs/reports/README.md` 取下一可用编号，更新索引、状态文档和必要架构说明。明确区分“已实现工具”“已执行实验”“推测”“真人验证”；不要将单条反馈扩写成全体玩家结论。
