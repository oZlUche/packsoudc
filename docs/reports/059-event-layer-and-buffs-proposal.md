# 059 · 设想：事件层（每个节点先过事件屏）、统一容器屏、局外 buff 与地图 buff

> 提议 ｜ 架构文档 6.2、6.5、9.2、15 节（v1.57）｜ 前一步：[058 作者五条提议](058-author-five-proposals.md)

作者在 058 第三轮又提了三样新东西（第一样「暂存区何时清」记在 058 第五节）。这三样比 058 那五条大：事件层改的是**每个节点怎么被处理**，
buff 是一套新的可组合构件。这里先整理、评估、给顺序，**都还没做**。

## 一、作者的原话与我的理解

### 1. 搜索和战利品是同一个界面

原话要点：搜索和战利品本质上是同一个界面，只是从不同的地方跳进来、内部装载的生成规则不同；「选择是否搜索」的那个界面是事件，见 2。

我的理解：一个**容器屏**：左边是渐进揭示的容器，右边是自己的棋盘与暂存区。尸体容器装的是掉落规则掷出来的东西，一次装满；搜索点装的是搜索规则，
「再搜一次」多装一批、多掷一次遭遇（5.4.2 的旋钮不变）。要不要搜、搜之前的文字与选项，不在容器屏里，在事件屏里。

与现状的差别：M6-2 已经是两块共用同一套视图和拖拽的屏，只差合成一个类、把「搜一次」按钮做成可选的。改动小。

### 2. 所有节点打开后先过事件屏

原话要点：所有节点打开后都先跳转事件界面；大部分没有前置剧情的战斗节点，事件被略过（变成类似转场的东西）；搜索节点和标准事件节点配置有文字、图像、选项框，
根据玩家的选项跳转不同的后续。

我的理解：节点的处理变成两段。**踩上去先出事件屏**：这个点配了事件就显示文字、图像、选项；没配（多数战斗点）就是一个转场，直接进后续。
**选项决定后续**：搜索点的事件至少有「搜索 / 离开」两项，选「搜索」才进容器屏；标准事件点的选项各有各的后果（给东西、回体力、给一个地图 buff、开一场战斗、什么都不发生、接下一个事件）。
事件是内容：`data/authoring/events/*.json`，文字、图像路径、选项、后果都在里面；选项可以带条件（有没有某个地图 buff、钱够不够），不满足就灰掉或不显示。

与现状的差别：现在 `NodeEvents.handle` 踩上去**立刻**把事做完（战斗当场打完、搜索当场开会话、事件按权重当场掷结果），没有停下来让玩家选的地方；
常规事件只有 item / restore / story 三种占位结果。

### 3. 局外 buff 与地图 buff

原话要点：局外 buff 由局外选项决定，可以修改各种机制（保留最大灵活性）；地图 buff 一般是强化或弱化，或者一个标记，用于在特定节点导向分支剧情。先占位，做一个简单的基础 buff 测试功能。

我的理解：两种 buff 是同一套构件、不同的生命周期。**局外 buff** 跨局，由局外的选择决定（占位：局外屏一个开关列表），效果落在各种机制上。
**地图 buff** 只在一局里，由事件的后果给，可以有效果（强化 / 弱化），也可以什么效果都没有、只是一个标记，事件选项的条件拿它导向分支。
「修改各种机制、保留最大灵活性」= 用 9.2 那棵效果树：效果按作用域分支，各系统只查自己那一档；新加一种可改的机制 = 加一个构件，不改基类、不改导入器。

与现状的差别：掉落那边留了 `MetaDropBonus` / `MapDropBonus` 两个返回 0 的占位来源（6.1）；效果树有 `MapEffect` 占位分支；此外没有 buff 的概念。

## 二、设计

### 容器屏

`ContainerScreen`（把 `loot_screen` 与 `search_screen` 合成一个）：装一个 `GridInventory`，可选地装一个 `SearchSession`；有会话就多一个「再搜一次」和风险行。
揭示按 058 第五条：当前一件 + 下一件、每档稀有度的秒数在 `SearchRules`、未搜的只能在容器内挪位。

### 事件层

```
EventDef（内容种类 events，data/authoring/events/*.json）
  id / title / text / image（路径，占位）
  options: Array[EventOption]
EventOption
  label
  requires: Array[Condition]      构件：HasMapBuff(id) / CanAfford(n) / VitalityAtLeast(n) …（注册表，可加）
  outcomes: Array[Outcome]        构件：GiveItem(pool) / RestoreVitality(n) / GrantMapBuff(id) / SpendMoney(n) /
                                        StartBattle / OpenSearch / Next(event_id) / Nothing …（注册表，可加）
```

节点怎么拿到事件：`NodeRules.events_by_type`（类型 → 事件 id 的权重表），战斗类型默认空 = 转场；随机点先揭开再按揭开的类型取。
事件本身也可以在生成地图时就按 `content_seed` 定进节点内容（5.3：内容由 content_seed 决定，读档一样）。

`NodeEvents.handle` 变两段：踩上去 → 取事件 → 有就 `event_pending`（存档里记着，读档回来还在这一屏）→ 玩家选一项 → 条件过了就依次执行后果 →
后果里的 `StartBattle` / `OpenSearch` 走现在的 `_fight` / `_open_search` → 点用过。没有事件的类型走现在的路（战斗直接打、商店直接开、休息直接回）。

搜索点的默认事件：文字「这里像是能翻出点什么」，选项「搜索」（`OpenSearch`）/「离开」（`Nothing`）；作者之后可以给具体的搜索点配别的文字和第三个选项。

### buff

```
BuffDef 复用 4.5 那份？不 —— 4.5 的 BuffDef 是战斗内的、每场重置。这里另起：
RunBuffDef（内容种类 run_buffs）
  id / display_name / description
  scope: META / MAP              局外的 / 一局里的
  duration_steps: int            地图 buff 走几步失效，0 = 整局；局外的忽略
  tags: Array[StringName]        标记用（事件条件查它）
  mods: Array[StatModifier]      战斗属性（编译时并入，和套装同一条路）
  rules: Array[AbilityRule]      战斗规则（同上）
  effects: Array[Effect]         跨域效果：LootEffect（掉落）、新增 RunEffect 分支
RunEffect（Effect 的第四个分支，EffectScope.RUN）
  VitalityMaxBonus(n) / StartingFundsBonus(n) / ExtraSearches(n) / ShopPriceMult(x) / RevealSpeed(x) …（注册表，可加）
```

生效点：`RunState.start` 读局外 buff 的 `RunEffect`（体力上限、开局钱）；`compile_player` 把两种 buff 的 `mods` / `rules` 与套装的并在一起；
`LootContext` 的两个占位来源改成真的（各自汇总 `LootEffect`）；`SearchSession` 问 `ExtraSearches`；事件条件查地图 buff 的 `tags`。
存档：`MetaState.active_buffs`（id 列表）、`RunState.map_buffs`（id、剩几步）。

测试功能（占位内容）：局外 `hardy`（体力上限 +1）、`lucky`（幸运 +1，掉落多一点）；地图 `marked`（纯标记）+ 一个事件「有标记才出现的选项」；
`weakened`（走 5 步内生命 −10%）。局外屏一个开关列表决定哪些局外 buff 生效，占「局外选项」的位。

## 三、性价比与矛盾

| 项 | 改动量 | 收益 | 矛盾 / 风险 |
|---|---|---|---|
| 容器屏合一 | 小 | 中 | 无 |
| 事件层 | **大** | 高：叙事与分支的地基，第 8 阶段内容扩充靠它 | `NodeEvents` 两段化，测试大改；存档多一个「待选的事件」；战斗事件的选项能不能「绕开」这一场要定（7.1：打不打是踩上去之前的一次性决定） |
| buff 骨架 | 中 | 高：一处构件、处处可改；事件分支的标记靠它 | 局外 buff 的「局外选项」现在只是开关列表；`MapEffect` 占位分支与 `RunEffect` 的边界要说清（前者改地图，后者改一局的规则） |

事件层的风险主要在**它改了所有节点的处理路径**：战斗、商店、休息现在是踩上去当场发生，改成先过事件屏后，没配事件的要严格等价于现在（转场 = 零帧、不改任何结果），
`test_node_events` 和 `test_game_flow` 的每一条都得守住。做法上先让「没有事件」走原路，再把「有事件」的那一段加上去，两条路并存。

## 四、顺序

把 058 与本篇合起来，建议：

1. **暂存区**：离开发生过事的点时清（058 第五节）、分层提示、设置。小。
2. **仓库格子化 + `MetaRules` + 结算屏一键置入 + 图鉴**。中。
3. **buff 骨架**：`RunBuffDef`、`RunEffect` 分支与注册表、生效点、两三个测试用的。中。
4. **事件层**：`EventDef`、条件与后果构件、`NodeEvents` 两段化、事件屏、搜索点的默认事件、容器屏合一。大。
5. **开局预选**：`CharacterDef`、初始包、从仓库往包里拖。中。
6. **搜索揭示**：当前 + 下一件、稀有度计时。中。
7. 节点外框：有了事件屏当每个节点的第一页，「进了这个点的一层」的感觉大半已经有了，外框可做可不做。

第 7 阶段侵蚀排在这些之后（作者定）。每一项一份报告。

## 五、要作者拍板的

1. 战斗节点的事件里能不能有「绕开这一场」的选项（7.1 说打不打是踩上去之前的决定；建议不能，战斗事件只做转场和剧情）。
2. 事件在生成地图时就定进节点，还是踩上去才按 `content_seed` 抽（建议生成时定，读档、预览都简单）。
3. 局外 buff 的「局外选项」是什么样（现在按开关列表占位）。
4. 地图 buff 的时限：整局 / 走几步 / 到下一个撤离点（建议数据字段 `duration_steps`，0 = 整局）。
5. 058 剩下的四条：件数 / 稀有度上限要不要；仓库空的第一局带什么；结算屏没置入的怎么办；带出的包进不进仓库。
