## 一处必须先说明的顺序依赖

要求是「插入一个道具导入程序」并「禁止把效果写死」。导入程序按要求排在 M2 之后，
但**它的数据模型必须现在就定**。

理由：触发时机／频率／连带触发是**战斗事件模型**的一部分。`BattleSim` 一旦按
「冷却到了就打一下」写出来，导入程序再想表达「受击时触发」「连带触发」就没有接入点，
只能推倒重写。所以本次先把效果系统的结构定下来，`BattleSim` 照着它实现。

## GDScript 的「接口」能力实测

设计前先在 4.7.1 上实测，不凭印象：

| 能力 | 结论 |
|---|---|
| `@abstract class` 不可实例化 | 可用，**解析期**报错而非运行时 |
| `@abstract func` 强制子类覆写 | 可用 |
| `Array[基类]` 装子类、多态派发 | 可用 |
| 运行时按脚本路径动态构造子类 | 可用 |
| `is` 判定 | 可用 |

GDScript 没有 Java／C# 意义上的接口与泛型，但 `@abstract` + 类型化数组足够表达这套结构。
额外好处：`@export var xs: Array[基类]` 在检视器里会自动列出**所有非抽象子类**供选择，
内容制作不需要手写类型名。

（实测用的探针脚本已删除，不入库。）

## 效果系统：三者分离

```gdscript
class_name AbilityRule extends Resource
@export var trigger: Trigger        ## 时机
@export var cadence: Cadence        ## 频率
@export var effects: Array[Effect]  ## 内容
```

物品的 `CombatProfile` 持有 `Array[AbilityRule]`，而不是「冷却 + 伤害」两个字段。
一件物品可以有多条规则：平时按冷却出手、受击时额外反击、开局给自己加护盾。

### 一切皆事件，连带触发不是特例

`BattleSim` 只推进时间并广播事件（`tick` / `item_fired` / `damage_taken` / …），
不知道任何具体效果。

**连带触发因此不需要任何特殊机制** —— 它就是一个订阅 `item_fired` 并判断来源是否落在
自己增益／受益格上的普通 `Trigger` 子类。如果把「连带触发」单列成字段，就等于又写死了
一种时机；做成事件订阅，它和其他时机地位完全相同。

### 频率独立于时机

命中不等于执行。`Cadence` 决定「这次命中要不要真做」：`CooldownCadence`、`EveryNth`、
`OncePerBattle`、`ChanceCadence`、`Always`。

收益很直接：「每 3 次攻击附带一次爆发」不需要新写触发器，
`OnItemFired` + `EveryNth(3)` 组合即可。三层各自可扩展，组合数是乘积而非加和。

### 确定性

规则求值按 `source_uid` 升序、同物品内按声明顺序。一切随机走 `RunRNG` 的 `battle` 流，
不得使用全局 `randf` —— 否则回放与批量模拟失效。

## 套装效果

```gdscript
class_name ItemSetDef extends Resource
@export var tiers: Array[SetTier]   # 每档：pieces + mods + rules
```

`ItemDef.set_id` 标明归属。两点定了默认但留了口子：

- **计数方式可配**（`INSTANCES` 每件算一件 / `DISTINCT_DEFS` 同定义只算一次），
  两种都有合理用法，不替设计做决定
- **档位累加而非互斥**：4 件套同享 2 件档与 4 件档。想要互斥就把高档写成增量，
  不为此增加机制

只数棋盘上的，暂存区不算，与 3.4 参战规则一致。

## 内容制作管线

```
data/authoring/items/*.json     人写的、可 diff 的源数据
        │  tools/import_items.gd   校验 + 生成
        ▼
data/items/*.tres  shapes/*.tres  sets/*.tres
```

### 为什么源数据用 JSON 而不是直接编辑 .tres

`.tres` 里数组与子资源的字面量手写极易出错，而且**写错时 Godot 常常静默留空**
（报告 004 已经踩过这个坑，当时的对策是用 `ResourceSaver` 生成）。JSON 可人写、
可脚本批量生成、diff 看得懂。

`.tres` 是生成物但仍然入库，否则每次 clone 都要先跑导入才能打开工程。导入器需幂等。

### 导入器不认识任何具体效果

这是整条管线的关键约束。导入器只做三件事：读 JSON、**按注册表**解析类型名、写 `.tres`。

```gdscript
const EFFECTS := {
    &"deal_damage": "res://core/battle/effects/deal_damage.gd",
    ...
}
```

新增一种效果 = 加一个脚本 + 注册表登记一行。导入器、`BattleSim`、编辑器三方都不用改。

### 校验比引擎严格

导入器是内容质量的唯一关口：id 唯一且与文件名一致、形状非空无重复、引用的套装／乘区／
属性键／类型名都存在、邻接标记格不与自身轮廓重叠、规则三项齐全。
**校验失败一律拒绝生成**，不产出半成品资产。

### 可视化编辑器作为后续增强

网格画笔涂形状与标记格、下拉选效果、实时预览编译结果。它**只是 JSON 的图形前端**，
产出仍进 `data/authoring/`，不绕过导入器 —— 这样手写与 GUI 两条路的数据完全等价。

## 遗留

- `CombatProfile` 目前仍是「`is_active` + `cooldown_sec` + `base_stats`」的旧形态，
  **本身就是一处写死**。实现效果系统时要改成 `Array[AbilityRule]`，
  届时报告 009 的编译器测试需要同步调整。
- 事件清单（`tick` / `item_fired` / …）目前只列在文档里，具体载荷字段等 `BattleSim`
  实现时定稿。
- 状态效果（Heat / Cold / Stun / 中毒）与 Mana 尚未建模，前者会作为 `ApplyStatus`
  的目标出现，后者可能需要在 `Cadence` 之外再加一层资源消耗判定 —— 到时再评估，
  现在不预先加抽象。
