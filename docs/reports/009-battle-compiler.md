## 关键决策

### 1. 插槽格必须与形状共用同一套平移量

这是实现中最容易出错、也最不显眼的一处。

`cells_rotated()` 的做法是「旋转后平移到 `min = (0,0)`」。插槽格在物品**轮廓之外**，
如果单独对它做旋转而不减去同一个平移量，物品一转，标记位置就和实际生效的格子错开。

因此给 `ItemShape` 加了 `transform_point(p, rot)`：内部记录每一步旋转的平移量
`_step_offset`，对任意偏移施加与形状完全相同的变换。

举例（L 形 `["##", "#."]`，星格在 `(2,0)` 即右邻）：rot1 时形状归一化会整体右移一格，
星格也必须跟着走到 `(1,2)`。测试里直接验证了「rot0 下邻不生效、rot1 后下邻生效」。

顺带把 `_build_cache` 重构成逐步记录平移量的形式。重构后既有 481 项断言原样通过，
说明变换等价。

### 2. 速度单独成一项属性，不去加成冷却

`HASTE` 基础 1.0，越大越快；`COOLDOWN` 是基础冷却秒数。

若把加成直接加在 `COOLDOWN` 上，按 4.3 的公式 `+20%` 会让冷却时间**变长**，也就是物品
变慢，与「+20% 急速」的直觉完全相反。分成两项后，「更快」就是速度变大，语义自洽，
公式也不用为冷却开特例。

`BattleSim` 取 `haste / cooldown` 作为每秒进度。

### 3. 编译是纯函数，且经过确定性验证

`compile()` 不读任何全局状态，不写回棋盘。测试里有一组专门验证：

- 同一局面、**不同放置调用顺序**，编译出的能力列表（def_id / 伤害 / 冷却 / 速度）完全相同
- 同一棋盘反复编译，结果逐位一致
- 能力列表按 `source_uid` 升序，顺序稳定

插槽点亮之所以能做到这一点，是因为它是**去重计数**而非匹配（4.2）。测试里直接钉了这条：
一件 1x3 的长条压住目标的 3 个星格，只算 1 份加成，而三件 1x1 各压一格则算 3 份。

### 4. 测试通道补了一个洞

写这一步时踩到：GDScript 的运行时错误会**中断所在的套件函数**，后面的断言静默消失，
而整个运行的退出码仍是 0。当时断言数从 524 掉到 517，日志里有一行
`SCRIPT ERROR: unsupported format character`（格式串里的字面 `%` 没写成 `%%`），
但运行照样报「通过」。

这种失败最危险 —— 覆盖率悄悄缩水，没有任何红色。现在 `tools/test.sh` 只要在日志里
发现 `SCRIPT ERROR` 就判失败并打印出处。

## 编译流程

```
compile(board):
  1. 收集棋盘上的非包物品，按 uid 升序     # 暂存区不参战
  2. 各物品从 CombatProfile 写入基础值
  3. 包体效果：按 bag_of() 施加给内容物
  4. 插槽点亮：
       把插槽偏移按物品朝向 transform_point
       数占住这些格的【不同物品】数量
       HOLDER → 持有者得「点亮数」份
       FILLER → 每个填充者各得 1 份
  5. 汇总 max_hp，主动物品产出 Ability
```

新增覆盖：

- 空棋盘只有基础生命值、无能力、DPS 为 0
- 主动物品产出能力并记录来源；包本身不产出能力；无 `CombatProfile` 的纯素材不参战
- 被动物品（`is_active = false`）贡献 `max_hp` 但不出手
- 暂存区里的武器不参战
- 包体效果只作用于自己装的东西；把物品挪进急速包后加成随之生效
- 插槽 FILLER 方向（磨刀石让右邻武器 10 → 15）与 HOLDER 方向（点亮 1 个 +20%、3 个 +60%）
- 插槽过滤器：`gear` 填不亮要求 `weapon` 的星
- **去重计数**：一件长条压住 3 个星格只算 1 份
- **插槽随物品旋转**：rot0 不生效、rot1 生效
- 包体乘区与插槽乘区分属不同乘区，按 4.3 相乘而非相加
- 确定性：放置顺序无关、重复编译逐位一致、能力按 uid 升序

## 遗留

- `BASE_HP = 25.0` 硬编码在编译器里，应随难度／章节配置化。
- `SocketProfile` 的 `Kind` 枚举定义了但未使用 —— 星与菱形目前靠两组独立字段区分，
  枚举留给将来可能的「插槽类型可扩展」需求。
- 尚无状态效果（Heat / Cold / Stun / 中毒等）的建模，属于 `BattleSim` 的范畴。
- 尚无 Mana 系统。
- 触发条件目前只有「按冷却自动出手」一种，`CombatProfile` 里还没有 trigger 字段。
  「受击时触发」「某物品触发时连带触发」这类要等 `BattleSim` 的事件模型定下来再加。
- `data/items/` 里的示例资产都还没配 `combat` / `sockets`，编译出来是空的。
  等 `BattleSim` 能跑之后一起补，届时才验证得了数值。
