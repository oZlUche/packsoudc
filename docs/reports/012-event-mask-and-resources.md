# 012 · 事件掩码与资源池

对应架构文档 v0.8：4.4 效果系统。**设计细化，不含运行时代码改动。**

## 采纳的建议

战斗中每个步骤（物品触发、效果叠层／减层、效果结算、生命扣除／恢复、耐力扣除／恢复）
都成为一次广播事件；为避免事件过多，**进入战斗时检查场上所有 listener，只开启被订阅的广播**。

这条建议直接被采纳。它同时暴露了原设计（v0.7）里的两处缺口。

## 缺口一：事件目录太粗

v0.7 只列了 `battle_start` / `tick` / `item_fired` / `damage_dealt` / `damage_taken` /
`hp_crossed` / `killed`。缺了效果结算、状态叠减层、耐力变动。

补全后按分组整理：

| 分组 | 事件 |
|---|---|
| 时间 | `battle_start` / `battle_end` / `tick` |
| 出手 | `item_fired` |
| 效果 | `effect_resolved` |
| 层数 | `status_stacked` / `status_unstacked` |
| 资源 | `resource_changed` |
| 存亡 | `died` |

## 缺口二：没有资源概念

「耐力扣除／恢复」这一条说明**耐力是一个可消耗的资源池**，而我此前只把生命当成一个数字，
根本没有资源这层抽象。

如果照着「生命一套事件、耐力一套事件」写，将来加法力、护盾值就得再各加一套 —— 又是写死。
因此统一为**资源池**：

```
resource_changed(key, delta, reason)
```

`key` 是资源键（`hp` / `stamina` / `mana` / …），`delta` 正负即恢复与扣除，
`reason` 说明来由（`damage` / `heal` / `cost` / `regen`）。

「生命扣除」与「耐力恢复」由此成为同一事件的不同取值。**新增一种资源不新增事件类型，
也不改 `BattleSim`。** 想只听生命下降，在 `matches()` 里判断 `key == hp and delta < 0`。

两个配套决定：

- **事件记的是实际变化量而非请求量。** 打到 0 封顶、超上限截断之后，
  「受到 50 伤害」和「实际掉了 12 点血」是两回事，监听者关心的通常是后者。
- **资源上限来自编译期的 `StatSet`**（`max_hp`、`max_stamina`…），
  所以「装备增加耐力上限」就是一条普通 `StatModifier`，不需要任何特殊处理。

## 事件掩码：三条必须守住的约束

实现本身很简单 —— 开战前把所有 `Trigger.subscribed_events()` 求并集，
`BattleSim` 发事件前查表，未被订阅的连 payload 都不构造。难的是下面三条。

### 1. 掩码取双方并集

A 方发出的事件可能被 B 方的物品监听（「敌人回血时我获得强化」）。按单侧算掩码会漏事件。

### 2. 规则集变化时必须重算

若某个效果能在战斗中授予新规则（`GrantRule`），新规则订阅的事件可能尚未开启，
那条规则就会**静默失效**。

这是最难查的一类 bug：没有报错、没有崩溃，只是某件物品「有时候不生效」。
因此授予规则的效果**必须**调用 `ctx.refresh_event_mask()`。重算很便宜，宁可多算。

### 3. 掩码是纯优化，必须不可见

测试里同时跑「全开」与「掩码」两条路径，断言两者产出的**事件日志与最终状态逐条相同**。

一旦掩码影响结果，说明它被误用成了游戏逻辑（比如有人靠「这个事件没人听所以不发」来实现
某个机制），必须立即修掉而不是接受现状。**性能优化混进语义是这类系统最常见的腐坏方式**，
而它一旦发生，后面所有人都会默认掩码是逻辑的一部分，就再也拆不开了。

这条测试的成本极低（同一份输入跑两遍比日志），但它是掩码能长期保持为优化的唯一保证。

## 顺带修掉的两个隐患

细化事件模型时发现 v0.7 还有两处没想清楚。

### Cadence 改为两阶段

「耗 10 耐力、冷却 2 秒的重击」需要把冷却与资源消耗组合起来。v0.7 的
`consume() -> int` 单阶段接口做不到原子：耐力不足时冷却已经被扣掉了。

改成两阶段：

```gdscript
@abstract func can_fire(ctx, state) -> bool   ## 只读
@abstract func commit(ctx, state) -> void     ## 确认执行，在此扣冷却／计数／资源
```

`AllOf([Cooldown(2), ResourceCost(stamina, 10)])` 先全体 `can_fire`，全过才逐个 `commit`。
**这与 `GridInventory` 的「先校验后写入」是同一个不变式** —— 那条不变式让跨容器移动的
回滚得以成立，这里让组合频率的原子性得以成立。

引入 `AllOf` / `AnyOf` 组合子后，频率层的表达力从「N 种」变成「N 种的任意组合」。

### 事件排队派发，不递归

同一逻辑帧内的事件**按发生顺序排队、逐条派发**，不允许递归立即派发 ——
否则「A 触发 B、B 又触发 A」会变成栈溢出而不是可控的连锁。

派发深度设上限，超限则丢弃并记一条警告事件。内容配错时应该能定位，而不是直接崩。

## 遗留

- 事件载荷的具体字段仍待 `BattleSim` 实现时定稿，目前只定了分组与语义。
- 状态效果（Heat / Cold / Stun / 中毒）的叠层规则（是否有上限、是否独立计时）未定，
  等 `ApplyStatus` 实现时一并处理。
- 耐力的具体作用（只是消耗品，还是同时像参照作品那样全局缩短冷却）未定。
  两种都能用现有结构表达：前者是 `ResourceCost`，后者是一条作用于 `haste` 的 `StatModifier`。
- 派发深度上限的具体数值未定，写进配置资源而非硬编码。
