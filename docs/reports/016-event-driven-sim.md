# 016 · 事件驱动模拟与构件清单

对应架构文档 **v1.1**：4.4 效果系统、4.7 模拟循环。新增 [`docs/effect-catalog.md`](../effect-catalog.md)。

## 一、去掉帧

原设计是 20Hz 定步长循环。指出后改为**事件驱动**：直接算出每次出手与每个 buff 到期的
精确时刻，在时刻之间跳跃。

这不只是修掉报告 015 里那个 `ONE / 20 = 3276.8` 被截断的 bug —— **那个 bug 根本不该存在**，
它是「模拟里有帧」这个前提的产物。`StatMath.tick_delta` 这个补丁已连同 `OnTick` 一并删除。

| | 定步长 | 事件驱动 |
|---|---|---|
| 误差 | `dt` 反复相加，除不尽的步长稳定跑偏 | 只在离散时刻改写状态，**零累积误差** |
| 开销 | 60 秒 = 1200 帧 × 全部规则 | 60 秒 = 几百个时刻 |
| 分辨率 | 被 20Hz 网格吸附 | 出手间隔可为**任意小数** |

测试里直接钉了这一条：0.37 秒冷却在 1.12 秒内触发 3 次，以及日志里**不存在 `tick` 事件**。

### 冷却按「工作量」计而非绝对就绪时刻

进度累积的是工作量：每秒推进 `haste` 点，攒满 `period` 点即就绪。

试过直接记「就绪时刻」，问题是一次急速加成会把**整段已走过的冷却**也一并缩短，
玩家会看到冷却条诡异地往回跳。按工作量记则只影响剩余部分：变速前把进度结算到当下，
之后按新速率外推。

## 二、实现中发现的分层错误

写测试时撞上一个死循环：`EveryNth`（攒够 3 次才放）挡住执行时**不推进冷却**，
于是调度器认为它仍然就绪，在同一时刻反复重试。

追下去发现这是**分层错的**，不是实现 bug：

> 按既定的消耗语义，「挡住了也照样走冷却」。`EveryNth`、`OncePerBattle`、`ChanceCadence`
> 的失败行为与「耐力不足」**完全一致** —— 它们根本不属于频率层。

重新划线：

| 层 | 职责 | 成员 |
|---|---|---|
| 频率 Cadence | **只管调度，不设卡** | `Always`、`CooldownCadence` |
| 消耗 Cost | 满足才执行，失败不退还冷却 | `ResourceCost`、`StatusStackCost`、`ChargeCost`、`UsesCost`、`ChanceCondition` |

顺带的收益：`costs` 本身就是列表且 AND 语义，**`AllOf` 组合子可以整个删掉**。
原先为它设计的两阶段 `can_fire` / `commit` 也不再需要处理多环节原子性。

这是实现反过来改进设计的一次 —— 如果只照着文档写，这个死循环会留到内容制作阶段
才以「某件物品有时候不生效」的形式冒出来。

## 三、BattleSim

```gdscript
while 双方存活 and now < 时限:
    next = min(自发规则的下次出手时刻, buff 到期时刻)
    if next 不存在: break            # 谁也打不死谁，判平局
    now = next
    结算这一刻：先到期，后出手
```

**先到期后出手**：正好此刻到期的增益不该再为这一刻加成，否则「buff 还剩 0 秒」
会变成玩家无法预期的运气。

**每条规则在同一时刻只尝试一次**：就绪却拒绝执行的规则不会重置冷却，
下一轮还会被选中，不记账就原地空转。

产出 `BattleResult`：胜负、时长、完整回放日志、终局快照。

## 五、一个必须知道的精度事实

时间与数值全程定点整数（1.0 = 65536）。`0.1` 这类十进制小数**无法精确表示**：
`round(0.1 × 65536) = 6554`，三次累加不等于 `round(0.3 × 65536)`，差 1/65536 秒。

实际偏差约 0.015 毫秒，玩家不可察觉。但它咬了我一次：测试断言「0.1 秒冷却在 0.3 秒时
触发 3 次」失败。**这不是 bug，是定点数的固有性质**，测试已改用 0.25 这类二进制友好的周期，
文档与构件清单都写明了这一点。
