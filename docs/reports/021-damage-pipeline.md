# 021 · 伤害结算管线、角色基线、增益槽连结

**阶段**：2 · M2　　**架构文档**：v1.8（新增 4.6，4.2 补两小节，原 4.6/4.7 顺延）
**测试**：835 项断言 / 13 个套件，全绿　　**基准**：单场 1.574 ms

---

## 起因

报告 020 之后照着构件表拼了一份[道具清单](../item-roster.md)，拼的过程压出四处
系统空缺。这一步修掉前三处，第四处（掉落效果没有消费方）按计划等 M4。

三处都是**用真实内容试着写，才发现写不出来**的东西 —— 光看接口是看不出来的。

---

## 一、角色基线：`base_hp` 升级成一张属性表

`BattleCompiler.BASE_HP = 25` 只管生命。耐力没有对应的基线，只能来自道具，
于是玩家开局捡到一把手枪、没捡到口粮，那把枪一发都打不出来，界面上还看不出为什么。

顺手补一个 `BASE_STAMINA` 常量能解决这一次，但下次加一种资源还得再补一个。
资源本来就是可扩展的（配一个 `max_xxx` 就多一种），基线必须同样可扩展：

```gdscript
class_name CombatantBaseline extends Resource
@export var base_stats: Dictionary = {}
const DEFAULT_STATS := {"max_hp": 25.0, "max_stamina": 50.0}
```

编译结果 = **角色基线 + 道具**。`compile()` 的第二个参数从 `base_hp: float`
换成了 `baseline: CombatantBaseline`。

**这同时是角色系统的占位。** 将来不同角色带不同的初始生命、耐力与其他资源上限，
届时由角色定义提供一份本资源即可，编译器与战斗一行不改。
测试里已经验证了这条路：给一份含 `max_mana` 的自定义基线，那个单位就凭空多出法力资源。

`ration` 口粮因此从「必需品」降级成「加量」，这也更像它该有的样子。

## 二、增益槽连结：连带触发终于配得出来

`OnItemFired` 原先只能用 `source_uids: Array[int]` 限定来源，而 uid 是**实例在
运行时**分配的 —— .tres 里根本不存在。于是「只在某把枪出手时触发」这条最典型的
连带触发，制作内容时写不出来。

按照「本作没有主武器设定」这条前提，正确答案不是加一个 `source_def_ids`，
而是**问邻接关系**：

```gdscript
enum Source { ANY, LINKED }
@export var source: Source = Source.ANY
```

`LINKED` 只听与本物品通过增益／受益格连结的道具。连结关系在编译期算好，
写进 `CompiledItem.linked_uids`：

- **对称**。「我给你加成」和「你给我加成」都算连着。非对称会让内容作者踩坑：
  把配件贴上去，却只有一边听得见对方。
- **过滤器不匹配就不算连结**。加成没发生，就不该有连结。
- 编译期算而不是运行时查棋盘 —— 战斗中背包本就冻结，这样战斗层完全不需要
  认识 `GridInventory`。

设计上这条落得正好：配件换个位置就失联，**摆放本身成了内容**，
而不是在配置文件里连一根线。

## 三、伤害结算：从一行减法拆成五步管线

原来的 `DealDamage` 里是这么一行：

```gdscript
var dealt := maxi(0, raw - armor)
```

新的管线：

```
1. 确认类型      能不能被护盾吸收、吃不吃护甲、要不要通知
2. 护盾吸收      能吸收则先扣护盾；中毒之类绕过
3. 受伤前效果    【同步派发】效果在这里改写伤害包
4. 计算受伤量    百分比 → 固定增减 → 反转 → 护甲，然后落到血量
5. 受伤后效果    发 damage 事件；间接伤害不招致反应
```

### 第 3 步是整条管线存在的理由

护甲那种**无条件**减伤，写成一个属性就够了。但这些写不进任何固定字段：

- 消耗 2 层格挡，减免 10 点
- 喝了解毒剂时，中毒伤害反转成治疗
- 全场一次，完全免疫一击

它们都有**前置条件**，而前置条件在本作里只有一种表达方式：消耗层。
所以受伤前效果必须是一条带扳机、带消耗的普通规则，只不过作用对象是
「正在结算的这一包伤害」：

```
on_before_damage(受到) · always · status_stack(格挡,2) · modify_damage(flat = -10)
```

它因此白拿了消耗层的原子性：**层数不够就不减伤，也不会白吃掉那几层。**
这一条有专门的测试。

### 唯一一处同步派发

普通事件一律入队，靠 `drain()` 逐条处理，连锁才不会变成栈溢出（v1.1 定下的）。
`before_damage` 是唯一的例外 —— 它必须在伤害算出来之前改到包，排队就晚了。

代价是允许有限重入：受伤前效果自己也可能造成伤害（荆棘反弹）。
因此有 `MAX_DAMAGE_DEPTH = 4` 兜底，达到上限时记一条 `dispatch_overflow`。
**但兜底不是防线** —— 真正让反伤不对轰的是下面那条类型语义。

`before_damage` 不进回放日志 —— 它没有可观测的结果，结果体现在随后那条 `damage` 上。

### 伤害类型的行为不写在结算里

```gdscript
class_name DamageTypeDef extends Resource
@export var shield_absorbable: bool   ## 能否被护盾吸收
@export var armor_applies: bool       ## 吃不吃护甲
@export var provokes: bool            ## 会不会招致反伤、吸血这类反应
```

| 类型 | 护盾 | 护甲 | 招致反应 | 用途 |
|---|---|---|---|---|
| `physical` | ✓ | ✓ | ✓ | 常规 |
| `fire` | ✓ | ✓ | ✓ | 元素线的起点 |
| `poison` | ✗ | ✗ | **✗** | 中毒：持续伤害 |
| `bleed` | ✗ | ✗ | **✗** | 流血：持续伤害 |
| `reflect` | ✓ | ✓ | **✗** | 反伤：反弹专用 |
| `drain` | ✗ | ✗ | **✗** | 流失 |

新增一种＝加一份资源并登记，管线一行不改。打错类型名会告警并退回常规默认值 ——
静默变成无敌是最难查的那种 bug。

### 反伤为什么不会无限对轰

第一版只有 `MAX_DAMAGE_DEPTH = 4` 这个递归上限。**那是兜底，不是解决** ——
撞上限意味着对轰仍然打了四轮，只是没打穿栈而已。

真正的答案是让**伤害类型自己声明会不会招致反应**（`DamageTypeDef.provokes`）：

| 类型 | 为什么不招致反应 |
|---|---|
| `poison` / `bleed` | 持续伤害每秒跳一次。若能招致反伤，一个中毒 buff 就把反伤刷成了主要输出，而玩家根本没在攻击 |
| `reflect` | A 反 B、B 再反 A，两件反伤道具会互相引燃 |
| `drain` | 能招致吸血的话，割自己一刀就成了正收益 |

于是对轰在**第一层**就终止，上限退回它该待的位置：内容把会招致反应的类型配进
反弹效果时，给一条可定位的告警。测试里两组用例形成对照 ——
手写 `deal_damage(physical)` 当反伤会撞上限并记下 `dispatch_overflow`，
而用 `reflect_damage` 的那组**根本碰不到上限**。

新增 `ReflectDamage` 效果，而不是让作者手写 `DealDamage`：

1. 反弹量取决于**这一下有多痛**，`DealDamage` 只读属性或固定值，拿不到伤害包；
2. 它**默认就用对了 `reflect` 类型**，作者不必记得填 —— 漏填就是一场对轰。

逃生口不变：扳机里**显式**写下类型名照样听得见。「中毒时净化」靠的就是这个。

### 流失：走管线，但不招致反应

`ChangeResource` 扣**血量**时不再直接改资源，而是造一包 `drain` 伤害走管线。
这样「以血换速」的超频模块同样吃得到减伤与免疫 —— 而那正是玩家最想用减伤
去抵消的一类代价。测试里验证了：流失绕过护盾，但受伤前减伤对它照样生效。

但流失**不该点亮反伤与吸血**，否则割自己一刀就成了正收益。
做法不是「不发事件」，而是在扳机那一侧过滤：

> `DamageTrigger.damage_type` 留空时只认 `provokes` 为真的类型；
> **显式填成 `drain` 就照样听得见。**

不发事件的话，「流失时触发」这类联动就永远没有接入点 —— 而那正是要留的口子。

### 护盾

`shield` 就是一种普通资源，由 `max_shield` 自动派生，配一个属性就有了。
它只是在管线第 2 步被优先扣除，能不能扣由伤害类型决定。

## 踩到的坑

写测试时三条断言挂了，根因是同一个：**派发顺序固定为先 side 0 后 side 1**，
而我让攻击方用 `on_battle_start` 开场就打 —— 那会赶在防守方布好护盾、
叠好格挡之前，测到的就不是想测的东西。

改成攻击方 `on_schedule + cooldown(1.0)`，推进到 1.5 秒再断言，
防守方的开场规则就有机会先跑完。这个坑写进了测试文件的注释：
**开场触发不适合用来测「防守方准备好之后挨打」的场景。**

## 验证

```
通过  835 项断言，13 个套件，耗时 1171 ms
2000 场：3148.7 ms，单场 1.574 ms
```

新增套件 `tests/test_damage_pipeline.gd`，覆盖：

- 类型注册表：内置六种的性质、内容追加、重复拒绝、未登记类型的告警回退
- 护盾：吸收、溢出见血、中毒绕过、没配护盾也不报错
- 护甲：常规减免、中毒无视、高于伤害时归零不倒扣、护盾吃完护甲再挡
- 受伤前：固定减伤、百分比、完全免疫、反转成治疗、只对指定类型生效
- 有条件减伤：层数够则减免并扣层，**层数不够则全额挨打且不白吃层**
- 流失：不点亮默认吸血、显式监听 `drain` 能听到、绕过护盾但吃减伤、
  非血量资源不走管线
- 反伤：`reflect_damage` 的对轰**在第一层终止且根本碰不到深度上限**；
  中毒／流血／流失不招致反伤，物理招致；显式监听 `poison` 的道具照样弹得回去；
  自伤不反弹；反弹量按护盾吸收后的待结算量算；反伤自己也吃对方护甲
- 深度上限（兜底）：故意把类型配错成 `physical` 手写反伤，验证它不把栈打穿
  并记下 `dispatch_overflow`

`tests/test_compiler.gd` 新增基线与连结两组，含一条对照断言：
同一块棋盘，`LINKED` 只补一次伤害、`ANY` 补两次。

**性能**：单场 1.305 → 1.574 ms，慢了约 20%。来源是每次命中多一次 `DamagePacket`
分配与两次类型查表。没有优化：2000 场 3.1 秒对实时 DPS 预估和批量平衡都够用，
而且这些开销换来的是减伤机制只实现了一遍。真到瓶颈时可以池化伤害包。
