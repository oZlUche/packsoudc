# 013 · 消耗层与战斗内增益系统

对应架构文档 v0.9：4.4 效果系统（新增消耗层）、4.5 战斗内增益系统、第 9 节 内容管线。
**设计细化，不含运行时代码改动。**

## 一、耐力与法力的语义（已定）

| 资源 | 谁消耗 |
|---|---|
| 耐力 | 大部分类型的**武器**每次出手 |
| 法力 | **法术书类**道具每次调动 |

默认消耗按物品类型给，但**写在物品定义里，不硬编码**。「不耗耐力的武器」只是一件
`costs` 为空的武器，不需要任何特例分支。

实际消耗走 4.3 公式结算（面板消耗 × 增益／减益），所以「减少耐力消耗 20%」就是一条
作用于 `stamina_cost` 的普通 `StatModifier`，与增伤减伤同一套机制。

## 二、消耗独立成第四层，并推翻了 v0.8 的一个设计

### 四层

```
时机 Trigger  →  频率 Cadence  →  消耗 Cost  →  内容 Effect
```

### 被推翻的部分

v0.8 把资源消耗放在 `Cadence` 里，用 `AllOf([Cooldown(2), ResourceCost(stamina,10)])`
表达，并**特意做了两阶段 `can_fire` / `commit` 来保证「耐力不足时不消耗冷却」**。

新的规则正好相反：**付不起则跳过效果，但冷却照常清零。**

这不是小改动，而是语义反转，原因是原设计有个我没想到的漏洞：

> 若消耗与冷却原子，耐力不足时冷却不走，武器会在耐力回满的**那一瞬间立刻打出** ——
> 等于耐力不足毫无代价，耐力管理不构成任何决策。

现在的语义下，耐力不足实打实损失一次出手机会，「带几把耗耐力的武器」才成为真正的取舍。

**架构文档里已写明这条不是疏忽、不要「修」它。** 否则后来人看到「检查失败却仍扣冷却」
很容易当成 bug 顺手改掉，而这恰恰会把耐力系统废掉。

`Cadence` 的两阶段予以保留，但用途收窄为**多个频率条件之间**的组合原子性
（`AllOf([冷却, 每场一次])`）。不原子的只是频率与消耗之间那一道。

### 等待队列：明确否决

考虑过「攒着，耐力够了再补打」。否决理由：多把武器排队时的优先级、队列长度上限、
队列里的武器要不要吃后来才生效的增益 —— 每一条都得新立规则，而收益只是让耐力不足
不那么难受。

留位不留实现：失败策略做成一个字段 `enum OnCostFailed { SKIP }`，目前只实现 `SKIP`。
不为一个尚未确定要不要的机制先建队列。

### 消耗是列表，且不止是资源

非武器道具通常没有消耗，但**检查环节一律保留** —— 后期必然出现「消耗 N 层某增益才能
触发」的效果，且可能同时消耗多种。

```gdscript
@abstract
class_name Cost extends Resource
@abstract func can_pay(ctx, source) -> bool
@abstract func pay(ctx, source) -> void
```

`AbilityRule.costs: Array[Cost]` 是 AND 语义：全部 `can_pay` 通过才逐个 `pay`。
**这一层内部仍然原子**，不允许出现「扣了耐力但层数不够」的半付款。

### 多规则、多效果都是列表

`ItemDef.combat.rules: Array[AbilityRule]` 与 `AbilityRule.effects: Array[Effect]`
两层都是列表。一条规则内的多个效果按声明顺序执行、**共用同一次消耗** ——
「付一次耐力，同时造成伤害并施加灼烧」是一条规则两个效果，不是两条规则。

## 三、战斗内增益系统

**战斗中一切属性变化都由 buff 承载，包括资源上限。** 「强壮」提供额外生命上限，
「病弱」降低生命上限，不为上限另开一套机制。

buff 仅在本场战斗内存在，结束全部清空。因此**参战属性在进入战斗时只读取一次** ——
这正是 4.1「编译期快照，战斗中不回头读背包」的直接后果，两者互相印证。

### 两套修饰必须分清

|  | 编译期修饰 | 战斗内 buff |
|---|---|---|
| 来源 | 包体效果、邻接标记、套装 | 战斗中由效果施加 |
| 时机 | 开战前编译一次 | 战斗中动态增减 |
| 生命周期 | 随背包布局 | 随本场战斗，结束清空 |
| 载体 | `StatModifier` | `BuffDef.mods`，同样是 `StatModifier` |

两者复用同一种 `StatModifier` 但**不是同一个系统**。由此产生一条必须写进 UI 的后果：
**战斗中改动背包不会影响本场战斗**。这不是 bug 是设计，别让玩家以为遇到了 bug。

### 运行时属性 = 编译快照 + 活跃 buff

`CombatantRuntime` 持有不可变的 `base: StatSet` 与可变的 `buffs`，
`stat(key)` 按 4.3 公式合并两者。按属性键设脏标记，只在 buff 增减时失效。

### buff 可以携带规则 —— 复合效果的关键

```gdscript
@export var mods: Array[StatModifier]   ## 每层一份
@export var rules: Array[AbilityRule]   ## buff 自己也能带触发规则
@export var on_apply / on_expire: Array[Effect]
```

「灼烧：每层每秒造成 2 点伤害」＝ 一条挂在 buff 上的
`OnTick` + `Cooldown(1s)` + `DealDamage(2 × 层数)`。
**`BattleSim` 里不需要为灼烧写任何特例**，它和物品的规则走完全相同的四层流程。

注意联动：施加带 `rules` 的 buff 会改变规则集，因此**必须重算事件掩码**
（报告 012 约束 2）。这是掩码那条约束的第一个真实用例。

## 四、buff 编辑器

与道具同一条管线：

```
data/authoring/buffs/*.json  →  tools/import_buffs.gd  →  data/buffs/*.tres
```

导入器复用同一套注册表解析 `mods` / `rules` / `effects`，因此 buff 编辑器几乎不额外
增加代码。**新增一种 buff 不写代码；新增一种效果才需要加脚本并登记一行。**

## 遗留

- **资源上限变动时当前值如何处理**已列入架构文档第 14 节待确认。推荐：上限增加则当前值
  同量增加（吃到「强壮」立刻多一截血，手感对得上），上限降低则按新上限截断。
  反过来会让「强壮」在满血时毫无即时反馈，玩家会怀疑没生效。
- buff 的叠层细则（多层是否独立计时、`RestackMode` 的具体取值）待实现时定稿。
- 护盾按资源池处理还是按 buff 处理尚未定 —— 两者都能表达，等有具体设计需求再选。
- `CombatProfile` 仍是旧形态（`is_active` + `cooldown_sec` + `base_stats`），
  延续报告 011 的遗留，实现效果系统时一并改造。
