## 二、流程上的做法

**先分步再动手。** 作者第一条提议来时，先写了 045 的四步规划再做第一步；后面每一步一个提交、一份报告，
架构文档同步改（每步一个版本号、一行变更记录）。作者中途补的经济一条按同样的节奏加成 M4-5，规划表里补一行。

**每一条作者的话都能在数据里找到对应的字段。** 这是 M4 最明确的工作方式：作者说「稀有度越高基础掉落率越低」，
就是 `DropRule.base_chance` 加一条「非递增」的导入校验；说「不会变成精英或 BOSS」，就是 `NodeRules.random_weights`
只认五个键；说「50 占位」，就是 `EconomyRules.extract_fee = 50` 写在 JSON 里。**规矩写进校验，数值写进 JSON，
代码里没有一个数**。作者定数的时候改 `data/authoring/` 下的文件、跑一遍导入，不用碰代码。

**每种内容都走同一条管线。** M4 给内容管线加了六种资产（enemies、enemy_pools、drop_rules、node_rules、economy_rules，
以及道具的流派标签），导入器一条通用 `_fill` 都喂进去了，只各写了一段校验。顺序在 `ContentPaths.ORDER` 一处：
后者按 id 引用前者（章节引用池与三种规则）。顺手加的 `tools/normalize_content.gd` 把作者数据重写成导出器格式，
仓库里的 JSON 从此就是「导出 → 导入 → 再导出」的不动点。

**测试的期望从数据推。** 六个套件里没有一个写死的期望数：件数范围来自档位表，掉落率来自规则表，遭遇概率来自曲线，
进账来自公式。改一份 JSON，测试跟着变。统计类断言（权重 9:1、概率 0.3、0.8）用一千次抽样、留宽容差。

**在 worktree 里做。** 主目录当时在另一条分支上带着未提交的地图改动，M4 全程在 `背包搜打撤-m4` 这个 worktree 里、
从 `main` 出发，每步快进推回 `main`。两边互不干扰，代价是作者要 `git merge main` 一次。

## 三、结果要点

### 1. 敌人就是一个背包，且是组装出来的

5.10 定的是「敌人 = 一块摆好道具的棋盘 + 基线」。M4-1 把「摆好」改成了「按规则组装」：`EnemyDef` 只写本色档位、
流派标签、基线覆盖、招牌道具；件数、棋盘、倍率由池的档位表按节点算出来。同一个拾荒者在外环背两件、在高危区背五件。
预览与真打走同一个 `BattleCompiler`（`EnemyKit.spec_of`），重建的棋盘直接是尸体容器。

**流派是标签**：道具 `tags` 里带 `burst` / `rapid` / `bleed` 就归到那个流派；混伤是同时带两个流派的敌人。
新增一种流派 = 打标签 + 写一个敌人。

### 2. 「哪个点该多强 / 该多肥」全是加法与乘法的表

`StrengthRule`（深度 + 危险 + 类型 + 难度 + 规模）、`DropResolver.owned_chance`（基础 + 难度 + 幸运 + 效果 + 来源）、
`EconomyRules.battle_reward`（(基础 + 每档) × 深度 × 难度）：每一项各管一件事，调哪个都看得出来。
深度一律按 tier 在全图里归一化，**形态无关** —— 手绘图也只看 tier。

### 3. 看得见的与看不见的

- 战斗 / 精英 / 核心的敌人**生成时就定好**（`EnemyPlacer.fill`），地图上悬停可见：名字、档位、生命、DPS、件数、预计掉落、打赢进账。
- 随机点生成时内容是空的，踩上去才揭开；搜索点的遭遇到掷中那一刻才造敌人 —— 存档里也没有。
  这两处是 5.10「唯一看不透的点」与「搜索的风险」的直接兑现。

### 4. 接缝都留了，且现在就在被调

- 局外 buff、地图 buff 对掉落的修正：`DropBonusSource` 两个方法，`MetaDropBonus` / `MapDropBonus` 占位加 0，`DropResolver` 现在就调它们。
- 珍宝类型：`treasure` 标签占位；仓库里还没有一件，测试断言「第一章掉不出珍宝」—— 作者定义了珍宝道具那条会红，提醒改成正面的。
- 撤离动作（M6）：`NodeEvents.pay_extract_fee` 已经在等它调。
- 玩家棋盘（M5）：`NodeEvents.player_spec` 是一个 Callable；沙盒给的是一块固定棋盘。

### 5. 随机数的纪律

一切内容随机只从节点的 `content_seed` 派生，每种用途一个标签（enemy / reveal / battle / loot / search / ambush:k / event / shop:n）。
同一局同一个点结果一样；改一种用途的抽法不影响别的；商店货架、搜索进度、随机点揭开的类型、付费撤离点都跟着图存，
存档只记「几次」「哪几格」这种不可推的量。

### 6. 沙盒现在能玩一整段

挑出生点 → 悬停看敌人 → 走上去打一场 → 掉落进日志、钱包进账 → 搜索点按两个按钮搜或走 → 商店买、刷新、走 →
休息回体力 → 到付费撤离点知道付不付得起 → 输多了战败。没有画面的部分只剩容器与棋盘的绘制、撤离本身。

## 四、过程中改过的判断

| 事 | 第一版 | 改成 | 为什么 |
|---|---|---|---|
| 敌人棋盘放不下 | 跳过那件 | 大件先摆、放不下换小件补，还差就在回报里列出 | 6×4 放不下「狙击 + 霰弹 + 撬棍 + 重甲 + 核心」；顺带给低档加了稀有度上限 —— 外环小兵不该背传说品，本来就该是设计 |
| 珍宝档位没道具 | 报错 | 记一笔 `treasure_missing`，不掉 | 作者说珍宝留空占位；没定义不是错 |
| 商店 | 只发信号 | 会话：买 / 刷新 / 走 | 作者补了经济 |
| 沙盒帧测试 | 「走到的点用过了」 | 搜索点要先离开 | 事件接上之后，用没用过由事件说 |
| 全套测试 240 秒超时 | 以为新套件慢 | 放宽到 480 秒 | 机器上开着两个 Godot 编辑器抢 CPU；新套件单独跑 1～3 秒 |
