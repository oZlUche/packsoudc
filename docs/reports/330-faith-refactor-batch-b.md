# 330 信仰重构 B 批：信力与祈愿分开、基础层与赐福层

- 来源：作者 2026-11-19 要求按 `handoff/2026-11-19-faith-system-implementation.md`（PR #663）实施信仰系统重构。本文是 B 批（方案 §3、§4、§9 B）。A 批见报告 329。
- 版本：v6.46
- 范围：花费从信力改成祈愿；派生赐福版在异神下保住原物品的功能。阈值、行为给点、六神效果都没改（方案 §3.1：「阶段 B 资源拆分时暂保留旧阈值」）。

## 1. 现在的规则

| | 信力（devotion） | 祈愿（prayer） |
|---|---|---|
| 用途 | 成长：阶只看它 | 消费：神坛「祈求赐福」、蛮神立即击败 |
| 变化 | 只增不减 | 进出都有，上限 100（`FaithDef.prayer_cap`，没配 = 100） |
| 来源 | 原来的行为构件、献祭 V、献祭生命上限 +20 | 打完一场有效战斗 +8（输赢都算，秒杀不算）；献祭 min(2V, 余量) |
| 花了以后 | 不会被花 | 信力不扣，阶不掉 |
| 改信 | 各神各一份，留着，不转给别的神 | 同左 |

- 所有数都是候选（方案 §3.2、§3.3）。
- 不奉神或者联系中断的时候，两样都不记（沿用 A 批：战后按开战时的快照 `CombatantSpec.faith` 记）。
- 悬浮窗的信力行后面写「祈愿 n / 上限」。神坛献祭预览照实写这次能进多少祈愿，满了写 0。

## 2. 扣费迁移（方案 §3.3「检索所有 `spend_points` 调用」）

| 原调用 | 分类 | 现在 |
|---|---|---|
| `AltarBlessPerk`（祈求赐福 40） | 消费 | `spend_prayer`，40 祈愿 |
| `SmitePerk`（立即击败 30） | 消费 | `spend_prayer`，30 祈愿；秒杀那一场不给祈愿 |
| `tests/run/test_blessings`、`test_brute_188b` | 测试 | 改成花祈愿；加断言「信力不扣」 |
| 存档迁移 | 迁移 | `RunMigrations._v5_to_v6` |

`FaithPower.spend_points` 删掉了，正式代码里没有扣信力的路径了。

持久结果按方案 §3.3 末条逐项定：

- 蛮神「献祭生命上限」：真付了生命上限，换来的信力或者「造成伤害 + 急速」算付过费的持久结果，原样保留。
- 日神「祈祷」的火焰层数：同上，算付过费的持久结果。
- 大地「锻炼」加的行数：同上。

这三项的新机制在 D 批（蛮神、日神）和 C 批（大地）里重做。

## 3. 神坛共享预算

- 神坛本来就是每个休息点一次特殊操作，跨信仰共享（`AltarModule.used` 按节点记，不分神），所以改信刷不出第二次。
- 方案里的「每个神坛成长额度 10」没有做：B 批保留旧阈值，在旧阈值下把献祭信力压到 10 会让一阶以上的效果基本够不着。这一条跟着 C、D 批换三阶阈值时一起上。

## 4. 基础层与赐福层（方案 §4）

| 类型 | 异神 / 不奉神时 | 对应信仰有效时 |
|---|---|---|
| 普通凡物 | 全部正常 | 全部正常 |
| 普通道具的派生赐福版（`blessed_of` 不为空） | **原物品的属性、规则、邻接、套装、生长都在**，只停 `faith_bonuses`；不压灰 | 再加神力层 |
| 手写的信仰道具（信物、赐福的长弓、赐福的盾） | 照 087：`dormant_keeps_combat` 开着的留自己的战斗定义，丢邻接、套装、信力加成；关着的不参战 | 全部生效 |
| 护符 | 不参战 | 生效 |

代码：

- `FaithState.keeps_base_layer(def)`：是派生赐福版。
- `FaithState.is_inert(def, active)`：整件休眠，也就是休眠、并且没有基础层。
- `BattleCompiler.compile` 第 1 步：派生赐福版休眠时记进 `unblessed`，只跳过第 4b 步的信力加成。邻接与生长照走。
- `_lit_neighbors`、`SetTracker`、`InventoryView` 画灰、`dormant_uids`（生长与悬浮窗「几件休眠」）都改读 `is_inert`。

派生版的基础层就是原物品复制过来的那份（`Blessings.derive` 只加了标签、`faith_bonuses`、稀有度和价值），不需要新字段。模板附带的标签（`add_tags`）在休眠时还挂着，邻居的邻接过滤器可能认它。目前的模板只加神的标签，邻接过滤器不认神的标签，所以没有影响。

## 5. 存档

- 一局档 v5 → v6（`RunMigrations._v5_to_v6`）：`faith_power`（一个池子 P）变成 `faith_progress` {神: {devotion: P, prayer: min(P, 100)}}。这是方案 §8.2 说的「一次明确的兼容补偿」：不恢复花掉的部分，也不从日志去猜。
- 已经有 `faith_progress` 的档不再动，所以重复迁移不会把花掉的祈愿补回来。
- 读档：负数清成 0，坏类型跳过，神 id 先过 `IdAliases.faith`。没走迁移的手造档只有 `faith_power`，照旧读成信力。
- 节奏表（`faith_history`）的行多两键 `prayer`（这一笔的进出）和 `prayer_total`，给校准看收入和支出。

## 6. 文本

- 帮助页 `altar_offering`（献祭换信力与祈愿）、`faith_power_and_tiers`（加一段讲祈愿）、`special_rites`（祈求赐福花祈愿）、`god_brute`（三阶花体力或祈愿）。
- 序章三 `tut3_rest_2`：「祈求赐福」花祈愿，括号里写怎么攒、花了不掉阶。
- 字表：`perk.prayer_short`、`faith.prayer`、`faith.prayer_line`、`log.offered_prayer`。`perk.bless_label`、`perk.smite_faith`、`perk.smite_summary` 改成祈愿。删了 `perk.faith_short`。
- `docs/gods.md`：两处花费改成祈愿，加一段写信力与祈愿。

## 7. 与方案的差异

- 每个神坛成长额度 10：没做（见 §3）。
- 祈愿「满足该神特色条件再 +2」：没做。特色条件是 C、D 批的新机制，到时候跟着加。
- 「无成功行为的即时逃跑不给」：逃跑本来就不发 `battle_finished`，不用改。
- 献祭生命上限换的 +20 只进信力、不进祈愿：它在方案 §3.2 里算「地图补充」的成长来源。
