# 014 · 两条定案：上限联动与战斗零操作

对应架构文档 **v1.0**：4.1 核心决策、4.5 战斗内增益系统、第 14 节待确认。
**设计定案，不含运行时代码改动。至此 M2 的设计冻结。**

## 定案一：上限增加时当前值同量增加

- 上限增加 → 当前值**同量增加**
- 上限降低 → 当前值按新上限**截断**

实现落在 `ResourcePool` 内部。上限变化本身发一条 `resource_changed`，
由此连带产生的当前值变化再发一条，`reason` 记为 `max_changed` ——
这样监听「生命恢复」的效果不会把上限变动误当成治疗。

架构文档第 14 节的待确认第 7 条随之删除，该表从 7 条降为 6 条。

## 定案二：战斗中没有任何玩家操作

**玩家的操作只发生在战斗之外；战斗中除了观看与跳过，没有任何操作余地。**

这条看着像 UI 约定，实际是架构级的。它把 4.1「模拟与表现彻底分离」从一个**划算的设计选择**
变成了**唯一可能的实现** —— 既然战斗过程不接受任何输入，整场战斗就必然可以在开战瞬间
一次算完。

由此确立四条硬约束：

| 约束 | 后果 |
|---|---|
| 胜负在开战瞬间即完全确定 | 「跳过」就是把播放游标推到日志末尾，不需要「加速模拟」这种东西 |
| `BattleView` 只有播放控制 | 倍速／暂停／跳过；**不接收任何指向战场的输入** |
| 战斗期间背包 UI 一律禁用 | 见下 |
| **`Effect.apply()` 必须同步完成** | 不得等待玩家输入，不存在「待玩家选择」的中间状态 |

### 顺带取消了上一版留的一个坑

v0.9 里我写过：「战斗中改动背包不会影响本场战斗。这不是 bug 是设计，别让玩家以为遇到了 bug。」

有了这条定案，正确做法不是**解释**这个行为，而是让它**发生不了** —— 战斗期间背包 UI
直接禁用。让一个会造成困惑的操作根本做不到，好过做得到却要写一段说明。

文档已相应改写。

### 对内容设计的硬约束

`Effect.apply()` 必须同步，意味着**任何效果都不能要求玩家做选择**。

想表达「三选一」，只能用随机（走 `battle` 随机流）或确定性规则（如「选当前血量最低的目标」），
不能弹窗。这一条要在做道具编辑器时守住 —— 编辑器不应提供任何「由玩家选择」的效果类型。

好处是效果系统省掉了一整套异步／挂起机制。代价是：如果哪天要加战斗中的玩家干预，
那不是加一个效果，而是推翻 4.1。文档里写明了这一点。
