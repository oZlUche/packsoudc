# 018 · 事件索引与冷却结算时机

对应架构文档 **v1.3**：4.4 效果系统。

## 起因

被问到「周期触发是怎么处理的」，并列出四种候选：全局定时器 / 个体定时器＋队列插入 /
提前计算触发时刻 / 多线程。

回答顺带暴露了两个问题。

## 当前的周期触发做法

四种都不是。`CooldownCadence` 的状态里只存两样：

```
progress   已完成的「工作量」
last       上次结算到哪一刻

next_time(now):
    progress += (now - last) × 速率      # 先把进度补到当下
    return now + (周期 - progress) / 速率 # 再按【当前】速率外推
```

`BattleSim` 每到一个时刻，重新问所有自发规则「下次什么时候」，取最小值跳过去。

**没有任何时刻被缓存**，所以减冷却／加急速在下一次查询时自动生效 ——
「提前计算触发时刻」那条的失效问题从根上不存在。进度记的是工作量而非时间，
变速也只影响剩余部分，不会把已走过的冷却一起缩放。

没用优先队列的理由正是这个：队列要缓存 key，而每次变速都会让 key 失效，
复杂度全花在维护上。当前是 O(n) 线性扫描，n 是自发规则数（几十条），
每场几百个时刻，总共几千次运算。

## 修正一：事件掩码升级为事件索引

原派发是朴素版：**遍历双方全部规则**，让每条自己判断是否关心该事件 ——
每个事件都要给每条规则分配一个 `RuleContext`，绝大多数当场丢弃。

改为 `_by_event: 事件名 → 订阅它的规则列表`：

- 派发从 O(全部规则) 降到 O(订阅者)
- **原来的 `_listened` 掩码是它的退化版本**（只回答「有没有人听」），已合并，两个结构变一个

`RuleRuntime` 增加 `owner_side: int`。存 int 而非 `CombatantRuntime` 引用：
单位持有规则、规则再反指单位就是引用环，`RefCounted` 永不释放 ——
这个坑在报告 015 已经踩过一次。

## 修正二：索引重建改为自动，因为漏调会出真 bug

原先只有 `ApplyStatus` 手动调 `refresh_event_mask()`，**移除 buff 时没有任何地方重算**。

对掩码来说这无害（只是多算几个事件）。但对索引是致命的：**残留条目会让已删除的规则
继续被派发**，表现为「某个效果明明没了却还在生效」，极难定位。

改为由 `CombatantRuntime._notify_rules_changed()` 在规则集变动时自动触发，
施加与移除两条路径都覆盖。调用方不需要记得任何事。

> 施加时漏调只是少触发，移除时漏调会让已删除的规则继续生效。
> 后者更糟，所以这件事不能靠约定。

## 修正三：冷却必须在变速之前结算

`RuleEngine.flush_all()` 写了却**从未被调用**。

后果：事件型规则（如「受击反击，内置冷却 2 秒」）的冷却只在其触发器命中时才结算。
若两次命中之间发生过变速，整段区间都会按**新**速率计算。

改为 `BattleSim._resolve_instant()` 开头就 `flush_all(now)`，且在处理 buff 到期之前 ——
到期本身就会改变速率。

## 验证

```bash
bash tools/test.sh
```

```
======================================================
通过  632 项断言，10 个套件，耗时 1051 ms
======================================================
EXIT=0
```

新增「事件索引」套件，重点补上此前**完全没有覆盖**的回归点：

- 施加带规则的 buff 后索引自动重建，无需调用方记得
- **移除 buff 后索引清空，已删除的规则绝不再触发**（修复前的真 bug）
- 自发型规则不进索引，但照常按时间轮出手
- 派发顺序稳定：side 0 在前，各方内部按登记顺序

## 遗留

- 索引在规则集每次变动时整表重建。规则数在几十这个量级，重建比维护增量更新便宜，
  但若将来单场战斗里频繁增删 buff，这里会变成热点。
- `evaluate` 仍为每条订阅规则分配一个 `RuleContext`。可以改成复用的 scratch 对象，
  但那样一旦有人把它存下来就会出错，目前不值得冒这个险。
- `mask_enabled = false` 现在只控制「未订阅的事件要不要构造入队」，派发始终走索引。
  「两条路径结果一致」的测试依然成立且依然有意义。
