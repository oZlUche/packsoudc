## 一、插槽模型的修正

### 核实到的机制

拿起或悬停物品时，它**轮廓之外的相邻格**上显示星形或菱形标记，那些格子就是它的插槽。
插槽格被别的物品占住即被点亮。点亮做什么由物品自己的描述决定，方向有两种：

- `HOLDER`：「★ 位置上的食物让**本物品**触发更快」—— 受益的是插槽持有者
- `FILLER`：「本物品触发时，连带触发 ★ 位置的物品」—— 受影响的是填充者

菱形与星形是同一套机制，只是第二种插槽类型，用于一件物品有两种不同效果时区分位置。

关键约束：**一件物品最多只能填另一件的一个星、一个菱形。**

### 我之前写错在哪

v0.4 里我写的是「本质上是一次带约束的二分匹配」，并为此设计了一套按 uid 升序的确定性
解析顺序。

由上述约束直接可得：

```
点亮的星数 = 占住星格的【不同物品】数量，上限为星格总数
```

这是个**去重计数**，天然与遍历顺序无关，不需要匹配算法，也不存在我担心的确定性隐患。
一个大件压住目标的 3 个星格只算 1 个，三个小件各压一格则算 3 个 —— 去重计数两种情形都对。

只有当同一件物品的多个星**含义各不相同**时才会退化成真正的匹配。已在架构文档里把
「同一件物品的所有星同质」写成硬约束，越线前必须先回去改那一节。

教训与报告 006 同源：我在没核实的情况下先设计，把一个计数问题想成了匹配问题，还为它
准备了不必要的复杂度。

## 二、数值约定

### 结算公式（已定）

```
终值 = 基础值 × (1 + A 类加成之和) × (1 + B 类加成之和) × … + 固定加值之和
```

- 同一乘区内**相加**，不同乘区之间**相乘**
- **固定加值在所有乘法之后相加，不吃任何百分比放大**

### 这条公式的设计后果

固定加值不参与放大，意味着它会随乘区堆叠自然贬值。好处是压住了「百分比 × 固定值」双向
叠乘造成的数值爆炸，固定来源天然成为前期战力。

代价要让内容设计知道：**后期想加强一件物品，加乘区远比加固定值有效**。如果某件后期物品
只给固定加值，它会显得越来越弱，这是公式决定的，不是数值没调好。

### 乘区是可扩展枚举

```gdscript
enum Buff { EMPOWER, SHARP, FIRE, HASTE }   # 追加只能加在末尾
```

结算时遍历枚举逐个乘 `(1 + 该区总和)`，不写死任何一类。新增乘区只需在末尾加一条，
公式自动多乘一个括号，`total()` 一行不改。

**为什么只能追加在末尾**：定点乘法带取整，乘法顺序影响末位。枚举声明顺序即乘法顺序。
在末尾追加一个空乘区，其因子恰为 `ONE`，而 `mul(v, ONE) == v` 逐位成立（测试里对多个
量级的 v 做了验证），所以历史数值不变；在中间插入则会重排乘法顺序，让所有已配数值和
存档对不上。

一项属性只会收到与它相关的乘区加成，无关乘区保持 0、因子为 1，因此不需要为每种属性
各开一套枚举。

### 定点数与取整

`ONE = 65536` 代表 1.0，与 4.4 的冷却累积同一套标度。

- 乘法**四舍五入**，负数向远离零的方向舍入以保持对称（GDScript 整数除法朝零截断，
  直接写 `(a*b + ONE/2) / ONE` 在负数上会偏，所以分符号处理）
- **只在最终应用伤害或显示时才转整数**。中途反复取整会让「两个 +5%」不等于「一个 +10%」，
  玩家算得出来，会当成 bug。测试里有一条专门钉死这一点
- 单个乘区减益总和低于 −100% 时，该乘区因子**钳到 0**。不钳的话叠够减益会把伤害翻成正的

固定加值不参与乘法，所以乘法部分被钳零后它仍照常相加 —— 这一条也有测试。

新增套件把公式的每一条性质都钉成了断言：

| 断言 | 钉住的约定 |
|---|---|
| 同区 +30% 与 +20% 得 150 | 同乘区内相加 |
| 跨区 50% 与 50% 得 225 而非 200 | 不同乘区相乘 |
| 100 × 2 + 10 = 210 而非 220 | 固定加值不吃放大 |
| 调用顺序不同结果相同 | 加成来源无序 |
| 所有乘区为 0 时终值逐位等于基础值 | 空乘区因子为 1，末尾追加安全 |
| 两个 +5% == 一个 +10% | 中途不取整 |
| 单区 −150% 得 0，两个 −150% 区不相乘成正 | 因子钳零 |
| 钳零后固定加值仍生效 | flat 不参与乘法 |
| 2.5 → 3，−2.5 → −3 | 取整对称 |

**这套断言就是约定本身。想改公式，必须先改测试。**

## 遗留

- `Buff` 枚举里的四项（EMPOWER / SHARP / FIRE / HASTE）是开发期占位，正式内容确定后替换。
  替换时注意：**只能在末尾追加，重命名可以，重排不行**。
- `SocketProfile` / `SocketEffect` 只在架构文档里定了形状，尚未落成代码，等 M2 编译器一起写。
- 冷却下限与各乘区的叠加层数上限尚未定值，架构文档要求写进配置资源而非硬编码。
- `StatValue` 每次 `new()` 都会分配一个 `PackedInt32Array`。编译期对每件物品的每项属性都要
  建一个，量大时可考虑池化，但现在远未到需要优化的规模。
