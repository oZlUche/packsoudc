# 069 · 设想：进阶难度 = 机制而不只是数值；伪 PVP —— 地图上移动的猎手

> 作者提议 ｜ 架构文档 5.7（侵蚀）、5.10 / 6.0（敌人与探索度）、7 节 ｜ 前一步：[068 搜索揭示](068-search-reveal.md)

## 一、作者的原话与我的理解

**进阶难度。** 类似杀戮尖塔的进阶，但更激进：不是单纯提升数值，而是加入机制。侵蚀就是打算在高难度加入的机制，所以可以再延后。

我的理解：难度不是一个乘数，是一份**清单** —— 每一档写明「开哪些机制、每个机制的参数、顺带哪些数值修饰」。侵蚀从「第 7 阶段必做」
变成「某一档难度开启的一个机制」，`MapTravel.erosion` 的钩子和顺序不动，只是谁来装它变了。

**伪 PVP。** 地图上出现不可视（或可视）的移动单位；不和节点互动（保留互动的选项，占位）；和玩家距离达到某个值以内时主动靠近并攻击
（或远离，可以设置多种行动逻辑）；强度实时变化，不按玩家背包里的道具，按玩家的探索程度 —— 运气好的玩家能轻易战胜，这是设计的正反馈；
追求每次对战胜率在 50% 浮动。

我的理解：一种新的实体「猎手」，住在地图的图上（位置 = 节点 id），每当玩家走一步它也走（沿边）；行动逻辑是构件（靠近 / 远离 / 游荡 / 埋伏……），
可视性是字段；强度在**开打那一刻**按当时的探索度现造（和随机点、搜索遭遇同一条路，6.0 的 `StrengthRule`），所以「实时变化」不需要它自己长；
「50%」不是对着这个玩家的背包算的，是对着**那个探索度上的参考玩家**调出来的一张表 —— 表调好了，背包比参考强的玩家就轻松赢。

## 二、设计

### 难度是内容：`DifficultyDef`

```
DifficultyDef（内容种类 difficulties，data/authoring/difficulties/*.json）
  id, level（0 = 普通）, display_name, description
  mechanics: Array[RunMechanic]     机制构件：每个带自己的参数（侵蚀：速度、深度阈值；猎手：几个、几步出现、行动逻辑……）
  effects: Array[RunEffect]         数值修饰，走 062 已有的 RUN 分支（体力上限、开局钱、商店价、幸运……）
  requires_level: int               解锁条件占位（局外成长定）
```

`RunMechanic` 是效果树之外的一个新抽象根（登记在 `EffectRegistry`，导入器 / 导出器 / 编辑器自动认得）：
`install(run: RunState)` 把自己接进一局 —— 侵蚀接到 `MapTravel.erosion`，猎手接到 `RunState.hunters`。**没有难度定义 = 普通难度 = 现在的一切**；
开局屏挑难度（和挑章、挑角色并列），`RunState.difficulty_id` 跟着存档。`ChapterDef.difficulty`（现在是个整数给敌人档位用）保留，
和这里的「进阶难度」不是一回事：前者是这一章本身多难，后者是玩家主动加的机制 —— 名字要分开（建议叫 `ascension`）。

### 猎手

```
HunterDef（内容种类 hunters）
  id, display_name
  visibility: HIDDEN / VISIBLE / NEAR（距离 ≤ N 步时可见）
  behavior: HunterBehavior          构件：approach（感知距离 D、每步走几步）/ flee / wander / ambush（不动，等你来）……
  engage_range: int                 0 = 同一个点才打，1 = 相邻就打
  enemy: 从哪个敌人池、按哪条 StrengthRule 现造（默认用这一章的池 + 一条猎手专用的 StrengthRule）
  node_interaction: 占位字段（现在恒为「不互动」）

猎手机制（RunMechanic 的一种，参数在难度里）
  count、spawn_after_steps、spawn_min_distance（离玩家至少几步）、hunter_ids（从哪几种里抽）
```

**一局里的状态** `RunState.hunters: Array[Hunter]`（位置、种类、活没活着、上次看见玩家在哪），跟着存档；随机数用 `RunRNG` 的一条独立流，读档接着走和没存过一样。

**回合。** 玩家 `step_to` 走完、这一步的节点事件处理完之后，猎手动：每个猎手按行动逻辑在图上走（`MapNavigator.distance_map` 给图距离）；
走完若任一猎手与玩家的距离 ≤ `engage_range`，立刻开打 —— 走 `NodeEvents._fight` 同一条路（`BattleSim.run`、`battle_finished` 信号），
flow 把回放排进队里，玩家看到的就是又一场战斗叠层。赢了猎手死、它的背包是掉落（敌人就是一个背包，5.10）；输了按战斗点的规矩扣体力（`loss_cost`，可以单列一档 `hunter`）。

**强度。** 开打那一刻 `EnemyPlacer.place_one` 现造，探索度参数就是现在的 `{"steps", "searches"}`，多一条猎手专用的 `StrengthRule`（对探索度更敏感）。
「50%」靠一个校准工具：`tools/bench_hunters.gd` 拿几套**参考背包**（按探索度分档：开局那套、搜过几次之后的典型、深处的典型 —— 内容，作者写）
对着猎手的档位表跑几千场，打印每档的胜率，作者调表到 50% 附近。参考背包是内容不是代码，所以「参考玩家」也是作者定的。

**可视性。** 可视的在地图上画一个标记（`MapView` 加一层）；隐形的什么都不画；NEAR 是折中 —— 靠近了才看见，给玩家一点反应时间。
隐形版建议给一句**模糊提示**（「附近有动静」，距离 ≤ 感知距离时显示在 HUD），否则被打就是纯随机惩罚 —— 要不要给你定。

**和现有规则的关系。** 猎手在某个点打了一场 = 这个点「发生过事」（`last_handled_id`），离开时暂存区清空（060 的规则，不另开例外）。
猎手不踩节点、不用节点、不改节点状态（作者：不和节点互动），`node_interaction` 占位。

## 三、性价比与矛盾

| 项 | 改动 | 收益 | 说明 |
|---|---|---|---|
| 难度定义 + `RunMechanic` 骨架 | 中 | 高 | 一次立住，侵蚀和猎手都往里装；开局屏多一列 |
| 猎手核心（实体、回合、三种行动逻辑、开打、存档） | 中大 | 高 | 图距离、敌人现造、战斗、存档全是现成的接口；新的是实体与回合 |
| 校准工具 + 参考背包 | 中 | 高 | 没有它「50%」只是愿望；参考背包要作者写 |
| 地图上的表现（标记、提示） | 小 | 中 | 可视版先做，隐形只是不画 |
| 侵蚀改成机制 | 小 | — | 钩子已在，只是换个装法；侵蚀本身仍是第 7 阶段的活 |

矛盾与要注意的：

1. **「50% 胜率」与「不看玩家背包」只能二选一地严格。** 只能对参考玩家 50%；对真实玩家是围绕 50% 浮动，浮动的方向由玩家的运气与选择决定 —— 这正是作者要的正反馈，但要接受「有的局猎手形同虚设、有的局必死」。
2. **隐形 + 强制开打 = 无法规避的惩罚。** 玩家没有任何决策空间时只有挫败感。建议至少一条：可见范围（NEAR）、模糊提示、或开打前一个事件屏（迎战 / 逃跑扣体力）—— 事件层现成。
3. **回合的定义。** 猎手按玩家步数走还是按行动点走？按步数简单直观；按行动点（贵的路猎手多走几步）更像追逐。建议先按步数。
4. **多个猎手会撞车**：同一步两个都到了 → 连打两场。建议同一步最多打一场，其余下一步再说。
5. **战败后猎手还在。** 打输了它就站在你旁边，下一步又打？建议打输后猎手撤走几步（或消失），否则是连环处刑。
6. **探索度是全局量**（总步数、总搜索次数），不区分「谁走得深」；猎手的强度表和随机点共用一套探索度，调一边会动另一边。给猎手单独一条 `StrengthRule` 可以隔离。
7. 侵蚀放进难度里之后，普通难度没有侵蚀 —— 与 5.7 原来的假设（每一局都有）不同，架构文档要改口。

## 四、建议顺序

1. `DifficultyDef` + `RunMechanic` 骨架 + 开局屏挑难度 + 存档（把侵蚀登记成一个空壳机制占位）。
2. 猎手核心：实体、按步回合、approach / flee / wander 三种行动逻辑、开打、存档、可视版标记。
3. 校准工具与参考背包；猎手专用 `StrengthRule`。
4. 隐形版与提示、开打前的事件屏（可选）。
5. 之后再回头做侵蚀本体（第 7 阶段）。

## 六、作者的回应（第一轮）

> 不同类型的角色可能拥有侦察、逃跑的技能，留一个接口。

落到设计上：**角色的技能是构件，走一局的上下文。** 062 已经有 `RunEffect` → `RunContext` 这条路（局外 buff 往上下文里加数，各系统在对应的点读）。
角色定义加一栏 `skills: Array[RunEffect]`（被动技能），开局时和局外 buff 一起编进 `RunContext`；猎手系统只读上下文，不认识角色：

| 上下文里的字段 | 谁读 | 意思 |
|---|---|---|
| `scout_range: int` | 猎手的可视性 | 隐形的猎手在这么多步以内对这个玩家可见（0 = 只按猎手自己的可视性）；侦察技能就是往这里加数 |
| `hunter_sense_mult: float` | 猎手的行动逻辑 | 猎手感知玩家的距离乘这个数（潜行类技能往下压） |
| `flee_cost: int` | 开打前的事件屏 | 逃跑扣几点体力；-1 = 逃不掉。有逃跑技能的角色把它压低或压到 0 |

于是「侦察」「逃跑」各是一个 `RunEffect` 构件（登记一行），角色文件里写 `"skills": [{"type": "scout", "range": 2}]`；
同一套构件局外 buff、地图 buff、事件后果也能给（临时的侦察效果就是一个带时限的地图 buff）。
主动技能（一局里按一下用一次）以后走事件层：开打前的事件屏多一个选项，条件是「有这个技能」（`has_buff_tag` 那一类的条件构件），后果是构件。
现在只留被动的接口，主动的等有了第一个真的技能再说。

开打前的事件屏于是从「可选」变成建议做：它就是逃跑技能的落点。

## 七、作者的回应（第二轮）：八个问题的答案

| 问 | 作者 | 落到设计上 |
|---|---|---|
| 1 距离与速度 | 按**绝对距离**算；所有数字不写死；按猎手等级生成配置表 | 距离是一个可换的度量（`MapMetric` 构件）：`steps`（图距离，core 自带）与 `absolute`（布局坐标，持有方把布局算出的坐标注入，单位按环距归一、不依赖像素）。感知距离、每步走几步、开打距离全在 `HunterDef` 里，一个等级一份文件（`hunters/hunter_1.json`……） |
| 2 打输了 | 保留所有选项：扣体力 / 不扣 / 必杀 / 猎手消失 / 猎手离开 / 赶走玩家并驻守 | 输了的后果是构件 `HunterLossOutcome`（登记表）：`spend_vitality(n)`、`nothing`、`kill`、`vanish`、`retreat(steps)`、`expel_and_guard`（玩家退回上一个点，猎手驻守原地）；一个猎手定义写一串，按顺序执行 |
| 3 打赢了 | 模板和普通敌人一样，掉落率更高 | 猎手就是敌人池里的一个敌人（`EnemyDef` + 档位），`HunterDef.drop_mult` 乘在掉落率上（`DropBonusSource` 那条接缝，6.1） |
| 4 数量与出现 | 不写死；默认在离玩家最远的点生成；数量看地图规模；行为有多种可选模板 | 生成规则在难度的猎手机制里：`count_by_scale`（规模 id → 几个）、`spawn: SpawnRule` 构件（默认 `farthest`：离玩家最远的点；以后可加 `random_far`、`at_type`……）、`behavior` 是构件 + 作者写的预设（approach / flee / wander / ambush / patrol） |
| 5 隐形与逃跑 | 进入感知范围时提示；可以逃，但不一定成功 | 玩家进入猎手感知范围 → HUD 与日志一句提示（信号 `hunter_sensed`）；开打前先过事件屏：「迎战 / 逃跑」，逃跑成功率与代价是 `HunterDef.flee`（构件 `FleeRule`：基础成功率、失败的代价），角色技能从上下文里改它（第六节） |
| 6 难度怎么选 | 局外解锁的特殊选项；名字随意 | `DifficultyDef.requires_unlock: StringName`（局外的解锁 id，占位；解锁系统随局外成长做），开局屏只列已解锁的；名字用「进阶」 |
| 7 50% 怎么调 | 系统完整后多场测试：每局按 3～5 个时间段取玩家装备配置，每个配置生成一个**平均木桩**，再生成猎手专属配置，不断和木桩对战保证 50% | 校准分两步：(a) 记录工具 —— 真实对局按时间段（步数分档）导出玩家棋盘的编译结果，多局平均成一个「木桩」（`CombatantSpec`，内容文件）；(b) 校准工具 —— 猎手专属配置对着每档木桩跑几千场，打印胜率、按目标 50% 建议档位。木桩是数据，猎手配置是数据，工具只做统计 |
| 8 多个猎手 | 各有各的范围，追玩家也不踏进别的猎手的范围 | 每个猎手一片**领地**（生成时按距离划：离它最近的那些点，或以它出生点为圆心的绝对半径），行动逻辑走路时只在自己领地内选点；玩家在两片领地之间也就至多被一个追。同一步开打至多一场自然成立 |

## 八、修订后的顺序

1. **难度骨架**：`DifficultyDef`（`mechanics`、`effects`、`requires_unlock`）+ `RunMechanic` 抽象根 + 开局屏挑难度 + `RunState.difficulty_id` 跟存档；侵蚀登记为空壳机制占位。
2. **猎手核心**：`HunterDef`（等级一份）、`MapMetric`（steps / absolute）、领地、`SpawnRule.farthest`、行动逻辑 approach / flee / wander / ambush / patrol、按步回合、感知提示、开打前事件屏（迎战 / 逃跑）、`HunterLossOutcome` 六种、掉落倍率、存档、地图标记（可视）。
3. **角色技能接口**：`CharacterDef.skills`（`RunEffect`）→ `RunContext` 的侦察距离 / 感知倍率 / 逃跑修正。
4. **校准工具**：木桩记录 + 猎手校准（系统完整后跑）。
5. 侵蚀本体。

## 九、作者的回应（第三轮）：专属池、段位

> 加一个猎手专属池占位。另外，我的意思是猎手的实际配置会根据玩家当前属于的段位变化（段位只受步数影响）。

落到设计上（报告 074）：

- **猎手专属池** `enemy_pools/hunters.json`（占位：和标准池一样的几种敌人与档位表，条目不限节点种类），两个占位猎手都指定 `"enemy_pool": "hunters"`。
  要给猎手专属的敌人配置，往这个池里加条目、改档位表就是。
- **段位只看步数。** 段位表在难度的猎手机制里（`HunterMechanic.bracket_steps`：第 k 段从第几步开始，占位 [0, 5, 10, 20]）；
  猎手定义里一张 `strength_by_bracket`（下标 = 段位，值 = 池里的档位，超出表长按最后一档）。开打那一刻按玩家当时的段位取档，**不看探索度、深度、危险**；
  表空才退回 071 的强度规则。木桩也按同一张段位表分段，校准表的 wanted 就是「这一段猎手表里的档」，和 best 并排 —— 调的就是这张表。
