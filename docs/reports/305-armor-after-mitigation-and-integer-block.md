# 305 护甲挪到扣血之前（血量的延伸）+ 穿透接口 + 格挡保持整数

> 作者 2026-11-11 17:12（查询线程）：「需要修改结算顺序，护甲吸收放在扣血之前，或者说护甲视为血量的延伸，但留一个以isPenetration的布尔为参数的接口方法，让某些特定伤害可以无视护甲」
> 作者 2026-11-11 17:13（查询线程）：「另外，格挡值我要整数，因此不能用乘法，考虑改成加法」
> 直接指派：待定按推荐派执行。

## 〇 一句话

两件事：① 护甲不再最先扣，改成**减伤、格挡、易伤都算完之后、扣血之前**的最后一层，吸收的是最终伤害；伤害包加一个「穿透」布尔，带它的这一下只跳过护甲，别的照算。② 品质不再给格挡 ×1.1，改成**每档 +1**，格挡的一切来源只许加减、不许乘。

## 一、现状（读码，main v5.80）

- `core/battle/damage/damage_resolver.gd` 五步：1 类型与火焰加成 → **2 护甲吸收**（48–58 行，吸的是原始值）→ 3 受伤前效果 → 4 百分比 / 固定减伤 / 反转 / 格挡（89–92）/ 受到伤害轴与按类型易伤（94–102）→ 落血 → 5 通知。
- 第 3 步的效果读 `DamagePacket.pending()` = `raw - absorbed`（护甲吸完剩多少）；`reflect_damage` 也按它算反伤。
- 现在跳过护甲的两条路：伤害类型的 `armor_absorbable = false`（中毒、流失、流血）；真实伤害 `pure`（流血类型、279 武器「其中 N 点真实伤害」），但 `pure` 同时跳过加成、受伤前效果、格挡和轴。没有「只跳过护甲」的口子。
- 281 寂灭的试炼（`only_damage_type`）：类型不对的那一下先不扣护甲，再在第 3 步后整包取消。
- 品质：`compiler.gd` `QUALITY_SCALED = [伤害, 格挡, 护甲上限]`，×(1 + 0.1 × 品质) 后向下取到定点（万分位），不是取整。现有格挡值 2 / 5 / 5 / 15，品质 1 变成 2.2 / 5.5 / 5.5 / 16.5。
- 格挡的其他来源：盾的基础值、加固 / 破绽轴、`stat_mod`（祝福盾）。目前数据里没有对格挡做乘法的修正。

## 二、做法

### 2.1 新的结算顺序

```
1. 确认类型；攻方火焰加成              （不变）
2. 受伤前效果（同步派发）              （原第 3 步；这时护甲还没动）
3. 计算受伤量：百分比 → 固定增减 → 反转 → 格挡（只对直接伤害）→ 受到伤害轴 → 按类型易伤
4. 护甲吸收：从第 3 步算出的最终伤害里扣，扣到护甲见底
5. 剩下的落到血量
6. 受伤后效果
```

- 第 4 步的条件：最终伤害 > 0、不是治疗（反转成治疗的不碰护甲）、类型 `armor_absorbable`、不是穿透、不是真实伤害。
- `packet.final` 仍是第 3 步的结果（护甲之前的最终伤害）；`packet.absorbed` 是护甲吃掉的；落血 = `final - absorbed`。事件与战记里「受到伤害」的数（`applied`）仍是实际扣的血。
- `pending()` 改成直接返回 `raw`（护甲还没吸）。**凡是读它的受伤前效果和反伤，含义从「护甲吸完剩多少」变成「这一下原本多重」**，执行逐条过一遍（见 §三.3）。
- 寂灭的试炼：类型不对的那一下在第 2 步后就取消，走不到护甲，原来那句特判可以删。
- 蛮神坚持期、死亡结算、治疗入口都在落血那一步，不动。

### 2.2 穿透接口

- `DamagePacket` 加 `penetration: bool`；`DamagePacket.create(..., p_direct := false, is_penetration := false)`，这就是作者要的以 `isPenetration` 为参数的接口（GDScript 命名写成 `is_penetration`）。
- 造成伤害的效果（`deal_damage` 一族）加同名可选字段 `penetration`，默认 false，作者以后给哪件道具填 true，哪件就无视护甲。
- 穿透**只**跳过第 4 步：火焰加成、受伤前效果、减伤、格挡、易伤照算。
- 类型上的 `armor_absorbable = false`（中毒、流失）保留，等价于「这个类型天生穿透」；真实伤害 `pure` 照旧跳过全部，自然也不碰护甲。三者在第 4 步合成一个判断。
- 本次不给任何现有道具加穿透（先少再多）。

### 2.3 格挡保持整数

- 把格挡从 `QUALITY_SCALED` 里拿出来：品质每档 **格挡 +1**（品质 1 = +1，品质 2 = +2），和规则里层数「每档 +1」同一个口径。伤害、护甲上限仍 ×1.1 不动。
- 现有四面：铜片 2 → 3 / 4，圆盾、塔盾 5 → 6 / 7，祝福盾 15 → 16 / 17。
- 规矩：**格挡只许加减**。导入时校验：对 `block` 的修正若是乘法 / 百分比，报错；格挡的基础值与修正值必须是整数。加固 / 破绽轴若有按比例的写法，改成按层加减（执行读 `_apply_axes` 确认，现状若已是加减则不动）。
- 显示：悬浮窗、`UpgradeCompare` 两窗、铁匠铺预览读的都是 `quality_stats` 的结果，跟着变；品质说明里「格挡 +10%」的字样改成「格挡 +1」。
- 旧档：品质是实例上的档数，格挡是编译时现算的，不用迁移。

## 三、要留神的地方（执行）

1. **护甲变硬了**：以前一点护甲抵一点原始伤害，现在抵一点减伤和格挡之后的伤害；有盾、有减伤的单位护甲耐久明显变长。反过来，带易伤 / 加时放大时护甲掉得更快。属预期，但基线必须重跑。
2. **平衡基线重跑**：`bench_battle` / `bench_matrix` 在改动前后各跑一遍，对照表进测试报告；基线假人只追加不改。报告 303 的难度候选（v5.80 的 D1–D3）是在旧顺序上测的，改完要重测后作者再定终值。
3. **读 `pending()` 的效果逐条列表**：「消耗格挡层减免」「够狠才触发」这类门槛、`reflect_damage` 的反伤比例，在回报里写清每条改前改后的差别；有哪条明显变味（例如反伤对有甲单位变强）就列出来问作者，不要悄悄改数。
4. **战记与内部日志**：`battle_trace` 的管线行顺序改成 原始 → 火焰 → 受伤前 → 格挡 → 轴 → 护甲 → 扣血；`battle_narrator` 的「挡下 N（护甲 a + 格挡 b）」数字来源不变，核对合计仍等于被挡掉的量。
5. **护甲完全吃掉的一下**：照旧发 damage 事件（扣血 0、`absorbed` > 0），「受到伤害时」类扳机的行为保持和现在一致，测试钉住。
6. **与合成锻造改造的关系**：改造方案新制造固定品质 0，但旧件的品质 1 / 2 保留，所以格挡每档 +1 仍然需要；两边都动 `compiler.gd` 的品质段，同一个执行线程按顺序做，避免冲突。
7. 架构文档 4.6 的管线顺序、`damage_resolver.gd` 头部注释同步改；测试：顺序（先格挡后护甲）、穿透只跳护甲、中毒 / 流血照旧、寂灭试炼、反转成治疗不碰护甲、品质 1 / 2 的格挡是整数、导入拒绝格挡乘法。
