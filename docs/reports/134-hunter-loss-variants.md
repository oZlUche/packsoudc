# 134 方案：猎手的战败结果分两种、生成时定，猎手战插进进点的事件队列

> 架构 · 提议（2026-10-06）。作者在「游戏反馈小修」里说：「猎手战不是节点，而是特殊类型的事件，理论上来说它会插入玩家进入的节点事件队列，如果战斗失败则玩家退回上一步，视为没有进入节点」；又说「保留两种情况，也就是猎手给的战败结果分为两种，生成猎手时会根据规则或者随机生成，保留添加其他结果的扩充性」。
> 本篇只提方案，作者确认后再实现。信力那半（猎手战按 `hunter` 记、狩猎之神 +30 生效）已在 PR #54 落地，不在本篇。

## 一、现在是什么样

- 战败后果写死在猎手**定义**上：`HunterDef.loss_outcomes` 是一串构件，按顺序全执行。
  - `hunter_1`：扣体力 → 猎手退走（`retreat`），玩家留在这个点。
  - `hunter_2`：扣体力 → 玩家被赶回上一个点，猎手驻守（`expel_and_guard`）。
- 同一种猎手每次生成都是同一个结果，没有「生成时定」这一步。
- 时序：走一步 → 这个点的事先发生（`_on_arrive` → `events.handle`）→ 猎手的回合（`on_player_step`）→ 玩家空下来才问够不够得着（`poke_hunters`）。
  - 所以猎手战现在排在节点的事**之后**。
  - 「赶回上一个点」只是把位置挪回去（`expel_player`），这个点已经算走过、它的事已经发生，谈不上「视为没进」。

## 二、方案

### 1. 战败结果 = 一个「结果档」，生成猎手时选定

新增 `HunterLossOption`（资源）：

| 字段 | 意思 |
|---|---|
| `id` | 档名，如 `repel`（击退）、`expel`（驱逐） |
| `display_name` | 给玩家看的名字 |
| `weight` | 随机时的权重，默认 1 |
| `outcomes` | 一串现有的 `HunterLossOutcome` 构件，按顺序执行（就是今天的 `loss_outcomes`） |

`HunterDef` 加两项：

- `loss_options: Array[HunterLossOption]`：这种猎手可能给的结果档。
- `loss_pick: HunterLossPick`：怎么选，是构件，登记在 `RunRegistry`，加一种 = 一个子类 + 一行。首批两种：
  - `random`：按 `weight` 随机（默认）。
  - `fixed`：固定第几档。

`Hunter`（活在图上的那个）加 `loss_id`：

- `spawn()` 时用 `loss_pick` 选一档，记下 id，跟着存档。
- 输了执行这一档的 `outcomes`。

兼容：只写了旧 `loss_outcomes`、没写 `loss_options` 的定义，导入时当作只有一档。旧存档里没有 `loss_id` 的猎手，也按第一档。

扩展口：

- 加新结果：写一个 `HunterLossOutcome` 子类，再在某个定义里加一档。
- 加新选法：写一个 `HunterLossPick` 子类，比如按段位、按难度、按地图规则选。
- 难度（`HunterMechanic`）可以覆盖权重，留成可选字段，首批不做。

### 2. 首批两档

| 档 | 输了之后 | 这个点算不算进过 |
|---|---|---|
| 击退 `repel` | 扣体力（节点规则的 `loss_cost.hunter`）；猎手退走、歇几步（`retreat`） | 算进了：这个点的事照常发生 |
| 驱逐 `expel` | 扣体力；玩家退回上一步（新构件 `expel`，不带驻守）；`expel_and_guard` 留作可选的第三种 | **不算进**：这个点不标走过，它的事不发生，回来再走一次才发生 |

`hunter_1`、`hunter_2` 都改成两档各一半，`hunter_2` 的驱逐档仍然驻守。数值全是占位。

### 3. 猎手战插进进点的事件队列

要让「驱逐 = 视为没进」成立，猎手战得排在这个点的事**前面**：

- 走一步 → 先移动猎手、判够不够得着。
- 够得着：先上猎手的事件屏（迎战 / 逃跑），这个点的事挂起。
  - 赢了、逃掉了、输了但是击退档 → 接着让这个点的事发生（就是今天的 `_on_arrive`）。
  - 输了且是驱逐档 → 退回上一步。这个点不标走过，不发「头一回到」，信力的「首访」也不记。
- 够不着：和今天一样。
- 走回已走过的点、事件挪人（`relocate`）、原地等（`wait`）都走同一套：先判猎手，再做这个点的事。
- 玩家正忙时被追上（`poke_hunters` 那条路）不变，照旧在空下来之后打。这时这个点已经进过了，驱逐档只退位置。

改动点：

- `RunState.step_to` / `relocate`：把猎手的回合提到 `_on_arrive` 之前，用一个「挂起的进点」记号接回来。
- `Travel` 标走过的时机要能推迟。
- `HunterSystem.fight` 返回档 id，让调用方决定接着进点还是退回。
- 存档：多存「挂起的进点」，读档时能接上，和 B1 修的搜索遭遇是同一类。

### 4. 玩家能不能事先看到是哪一档

建议能看到：猎手被感知后，悬浮说明和开打前的事件屏写「输了会被击退 / 驱逐」，让「迎战还是逃跑」有依据。

## 三、待定（括号里是推荐）

1. 选法首批只做随机和固定，还是也做按段位？（只做随机 + 固定）
2. 驱逐时，走这一步花的体力 / 时间算不算？（算：步数照走，只是没进点）
3. 驱逐档的猎手要不要驻守？（不驻守；`expel_and_guard` 留作 `hunter_2` 的第三种选项）
4. 玩家能不能事先看到档？（能，感知之后显示）
5. 正忙时才被追上的那种（事已经发生），驱逐只退位置？（是）

## 四、测试

- 生成时按权重选档；固定选法给定档；旧定义和旧存档都按第一档。
- 击退：输了留在点上，这个点的事照常发生。
- 驱逐：输了退回上一步，这个点没标走过、没发生事、没记首访；再走过去，事照常发生。
- 猎手在进点前开打：赢了或逃掉，接着发生这个点的事。
- 挂起的进点能存读档。
