# 032 · M3-2 生成器抽象、通用校验与换种子重试

> 阶段 4 · M3 ｜ 架构文档 5.3（v1.31）｜ 计划见[报告 027](archive/027-m3-plan.md)

## 目标

把「造一张图」与「造出来的图合不合格、不合格怎么办」分开。
前者每种地图形态各写一遍，后者只写一遍。

## 产出

| 文件 | 职责 |
|---|---|
| `core/map/map_generator.gd` | `@abstract`。子类只实现 `build`；校验与重试由基类包办 |
| `core/map/map_validation.gd` | 一次校验的结果。失败带 `rule` 键，可跨尝试聚合 |
| `core/map/map_generator_registry.gd` | `generator_id → 脚本路径`，照 `EffectRegistry` 的样子 |
| `tests/test_map_generator.gd` | 四组：通用校验 / 重试 / 确定性 / 注册表 |

## 关键决策

### 1. 子类只实现「造一张图」

```gdscript
@abstract func build(cfg, rng) -> MapGraph      # 子类写这个
func generate(cfg, base_seed, attempts) -> MapGraph   # 基类包办校验 + 重试
```

分开之后，「失败了换个种子再来」只写一遍。M3-3 的环形生成器、M3-3b 的手绘解析器
都不必各带一份重试循环——而两份重试循环迟早会在「上限是多少」「失败怎么报」上分岔。

子类重写 `validate` 时**必须先调 `super`**：环形图的配额、覆盖、路线是它自己的规矩，
但「图得连得上、出生点得有、终点得到得了」是所有形态共通的。

### 2. 失败原因按规则**跨尝试聚合**

这是 `MapValidation` 存在的理由，也是它没有复用 `ImportReport` 的理由。

导入器的消息定位到**文件里的一个字段**（`rifle.combat.rules[0].cadence.seconds`）；
这里定位到**图上的一处**，而且要能跨几十次尝试统计：

```
各条规则失败次数：reachable × 28，coverage × 3，quota × 1
```

「32 次里 28 次是全图不连通」直接告诉你该调连通性相关的参数。
只给最后一次的细节则什么也说明不了——最后一次失败在哪条规则上，很大程度是运气。

所以每条失败带一个 `rule` 键（`&"reachable"`、`&"goals"`…），聚合按它来，
消息本身写给人看。

### 3. 每次尝试的种子单独算得出来

```gdscript
static func derive_seed(base: int, attempt: int) -> int:
	return hash("%d:%d" % [base, attempt])
```

另一种写法是让重试共用一个 rng、自然往下取。那样也确定，但要复现「种子 12345 的
第 7 次尝试」就得把前六次重放一遍——而调生成器时，你想看的恰恰是失败的那一次。

没有自己写 splitmix 那类位运算混合：**GDScript 的 `>>` 对负数是算术移位**，
照搬过来会在负种子上悄悄失真。`hash(字符串)` 稳定、够用，而且一眼看得出对不对。

### 4. 死胡同是合法的

通用校验里最容易写错的一条。「每个节点至少两条边」看起来很合理，
但这一章的规则是**可以走回头路**——走进死胡同再走出来，代价是行动点，
而行动点正是压力所在（5.4）。

所以校验只拦「一条边都不挨着」的孤立节点，不拦死胡同。测试里专门放了一个死胡同
断言它是好图。

### 5. 注册表先空着，但检查已经架好

`GENERATORS` 现在是空表——`ring` 在 M3-3 登记，`grid_script` 在 M3-3b。
测试遍历表里每一条，检查它指向的脚本**真实存在**且**确实是 `MapGenerator` 子类**。

现在这条是空转。等表里有了东西它就开始干活：路径打错要在这里红，
而不是等某一章跑不起来才发现。这是「期望值从数据推」那套做法用在注册表上。

## 验证

```
godot --headless --path . --script tests/run_tests.gd
通过  1509 项断言，23 个套件
```

假生成器造的图刻意**不像同心环**——一条链、一个孤岛、一个断开的点，
每个都是用来踩某一条通用规则的最小例子。这一层不认识任何形态，
用某种形态来测它就等于把形态偷偷引进来了。

> 跑测试时会看到三段 `push_error` 输出，那是「重试用尽」的用例在演示错误信息长什么样，
> 不是测试失败。末尾的「通过」才是结论。

## 遗留

- 注册表是空的，两个生成器分别在 M3-3 与 M3-3b 落地。
- `validate` 目前一条规则失败会继续检查后面的（收集完整的失败清单），
  节点很多时会产生很长的消息。`to_text` 默认只列前 6 条，够定位就行。
- 批量统计脚本（跑 200 个种子看 `attempts_used` 分布）等 M3-3c，那时才有真配置可调。
