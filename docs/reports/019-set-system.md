# 019 · 套装系统

对应架构文档 **v1.4**：新增第 9 节「套装系统」（原 4.6 删除，其后各节顺延）。

## 与原设计的两处偏差

| | v0.9 写的 | 实际要求 |
|---|---|---|
| 计数与激活 | **编译期**数一遍 | **背包层持续维护**，拖入即记，UI 实时暗／亮 |
| 效果类型 | 只有 `mods` + `rules` | **还要能影响掉落** —— 战斗之外的作用域 |

第二条是关键。`StatModifier` 和 `AbilityRule` 都只在战斗里有意义，「提升战胜后的战利品
掉落」根本装不进去。硬塞的话，要么逼掉落系统去理解 `StatModifier`，
要么逼战斗系统去理解掉落表。

## 作用域：各系统只查自己那一档

```gdscript
@abstract
class_name SetEffect extends Resource
@abstract func scope() -> StringName
```

| 子类 | 作用域 | 谁来取 |
|---|---|---|
| `CombatSetEffect` | `combat` | `BattleCompiler` |
| `LootSetEffect` | `loot` | 掉落系统（M4，**尚未实现**） |

`SetTracker.effects_in_scope(scope)` 是唯一入口。**新增作用域 = 加一个子类 +
对应系统去查询**，不改基类，也不动其他系统。

`LootSetEffect` 现在就存在且有测试，是为了证明这层抽象确实容纳得下战斗之外的效果 ——
而不是等做掉落时才发现套装塞不进去。一个档位里可以混放两种作用域。

## 激活在背包层

```
拖入／取出棋盘 → GridInventory.changed
      → SetTracker.recount() → activation_changed → UI 暗／亮
```

- **只数棋盘上的**，暂存区不算（与 3.4 参战规则一致）
- **包不算部件**，它是承载物，即便标了 `set_id` 也不计入
- 档位**累加**而非互斥；计数方式可配（`INSTANCES` / `DISTINCT_DEFS`）
- 物品身上的套装信息**纯粹是 UI 提示**，效果写在 `ItemSetDef` 上

编译器不认识 `SetTracker`，也不自己数件数，只接收一个已筛好的效果列表。

## 实现中挖出的两个真 bug

都是上一步 `default_base`（为 haste 这类乘法单位元属性设 1.0）带来的连锁。

### 1. 单位级属性聚合把 haste 累加了

`from_spec` 把各物品属性求和进单位表。`ensure(HASTE)` 先以默认 1.0 建值，
再逐件 `+= 1.0` —— **N 件物品 = N+1 倍速度**。

测试里套装的周期性规则本该每秒一次，实测每 0.5 秒一次（棋盘上 1 件物品 → haste 2.0）。

修正：`BattleStats.default_base(key) != 0` 的属性**跳过跨物品累加**。
单位级 haste 的含义本就是「不属于任何物品的规则用什么速率」，理应是 1.0 起。

这个 bug 会随物品数量放大 —— 满背包时套装与 buff 规则会快到离谱。

### 2. 单位元属性缺席时返回了调用方的 fallback

`total_of(key, fallback)` 在键不存在时返回 `fallback`。修完 bug 1 之后，
单位级 HASTE 不再被写入，于是读出 0 —— 冷却被放大上万倍。

修正：**单位元类属性缺席时返回自身的单位元**，不走 fallback。
靠每个调用方记得传 `StatMath.ONE` 是不可维护的，漏一处就出这种事。
属性的单位元是属性自身的性质。

## 验证

```bash
bash tools/test.sh
```

```
======================================================
通过  699 项断言，11 个套件，耗时 1025 ms
======================================================
EXIT=0
```

新增套装套件（四组）：

- **背包层计数与激活**：拖入即计入并发信号；档位累加；无 `set_id` 的物品与包都不计入；
  取走即失活；UI 进度 `{count, next, active}`
- **计数方式**：`DISTINCT_DEFS` 下两把同样的剑算 1 件，`INSTANCES` 下算 2 件
- **作用域隔离**：同档混放两种作用域，各系统只拿到自己那条；失活后两侧都取不到
- **编译期并入**：`SET_PIECES` 目标只加给部件、`ALL_ITEMS` 加给全体；
  套装自带的周期性规则确实在战斗中出手

外加单位级属性聚合的回归测试（加法属性求和、单位元属性不累加、空单位读 haste 为 1.0）。

性能未受影响：单场 1.290 ms。

### 两处测试自身的错误

- `_set` 与 `Object._set(StringName, Variant)` 虚方法签名冲突，改名 `_set_def`
- `ResourcePool.snapshot()` 返回的已是取整后的整数，我又套了一层 `to_int`，
  79 被再除一次成了 0

## 遗留

- `LootSetEffect` 只有数据没有消费方，等 M4 掉落系统。
- `data/sets/` 为空，尚无套装资产；内容管线（第 10 节）要加 `import_sets.gd`。
- UI 尚未显示套装进度与暗／亮切换，`activation_changed` 与 `progress_of()` 已就位。
- `SetTracker` 每次棋盘变动全量重算。棋盘物品数在几十这个量级，重算比增量维护便宜，
  但拖拽过程中每帧触发的话需要观察。
- 单位级属性目前只有 `armor` / `max_hp` 真正用到求和语义，其余键的聚合意义未逐一审视。
